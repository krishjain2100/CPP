`std::shared_mutex` and `std::shared_lock` were introduced in C++14 and C++17.

### The Problem with Standard Mutexes

- 100 threads are constantly **reading** a data.
- 1 thread occasionally **writes** (updates) the data.

If you use a standard `std::mutex` with `std::lock_guard`, your code looks like this:

```cpp
// 100 threads are calling this simultaneously
int getPrice(string asset) {
    std::lock_guard<std::mutex> lock(mtx); // Blocks everyone else!
    return priceMap[asset];
}
```

Multiple threads reading the same memory at the same time is 100% thread-safe, as long as no one is modifying it.

---
### The Solution: `std::shared_mutex`

A `std::shared_mutex` allows a single mutex object to be locked in two completely different ways:

1. **Shared Lock:** Multiple threads can acquire a shared lock simultaneously. If 50 threads want to read data, they can all pass through the lock at the exact same time without blocking each other.
    
2. **Exclusive Lock:** Only _one_ thread can acquire an exclusive lock. The moment a writer asks for exclusive access, it blocks _all_ new readers and waits for existing readers to finish. No one else can read or write while the writer holds this lock.

---
### The Two RAII Wrappers

To implement this, C++ uses two different RAII wrappers on the **exact same** `std::shared_mutex`:

- **For Readers:** You wrap the mutex in **`std::shared_lock`**. This requests _shared_ access.
- **For Writers:** You wrap the mutex in **`std::unique_lock`**. This requests _exclusive_ access.


```cpp
#include <iostream>
#include <shared_mutex>
#include <map>
#include <string>

class ThreadSafeDatabase {
private:
    std::map<std::string, int> dataMap;
    std::shared_mutex dbMtx; // The shared mutex

public:
    // --- THE READER PATH (Shared Access) ---
    // Multiple threads can run this function at the EXACT SAME MICROSECOND.
    int readData(const std::string& key) {
        std::shared_lock<std::shared_mutex> readerLock(dbMtx); 
        // Critical Section (Read-Only)
        return dataMap[key]; 
    } // readerLock out of scope -> releases shared access

    // --- THE WRITER PATH (Exclusive Access) ---
    // If a thread enters here, ALL readers are blocked until this finishes.
    void writeData(const std::string& key, int value) {
        std::unique_lock<std::shared_mutex> writerLock(dbMtx); 
        
        // Critical Section (Modifying Data)
        dataMap[key] = value; 
    } // writerLock out of scope -> releases exclusive access
};
```

---
### The Rules of the State Machine

The operating system manages the threads under `std::shared_mutex` using three simple rules:

- **Reader inside?** Other readers can enter immediately. Writers must wait.
    
- **Writer inside?** Everyone (readers and other writers) must wait.
    
- **Writers waiting?** Most modern OS schedulers prioritise the writer. If a writer is waiting in line, new readers are blocked from entering so the writer doesn't get starved of execution time forever.  If you remove this rule, then readers keep entering the door while writers are just waiting.

---
### Caution

`std::shared_lock` has a slightly more complex internal instruction set than a standard lock, making it slightly slower than a regular `std::mutex` if only one thread is using it.

- **Use standard `std::mutex`:** If your threads are doing a mix of 50% reading and 50% writing.

- **Use `std::shared_mutex`:** Only when you have a **massive asymmetry** (e.g., 95% reads, 5% writes), and your readers are frequently blocking each other.
