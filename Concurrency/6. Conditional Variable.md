Imagine a scenario: one thread downloads images (Producer), and another thread applies a filter to them (Consumer). The Consumer cannot work until an image is ready.
### 1. Bad Way

``` cpp
void consumer() {
    while (true) {
        mtx.lock();
        if (image_ready) {
            processImage();
            image_ready = false;
            mtx.unlock();
            break;
        }
        mtx.unlock();
    }
}
```

**Why is this bad?**  The consumer locks the mutex, checks the flag, unlocks, and repeats. This pegs a CPU core to 100% usage doing absolutely nothing, draining battery and stealing execution time from the Producer.

---
### 2. `std::condition_variable`

A Condition Variable allows a thread to say: _"I am going to sleep. Do not schedule me on the CPU. Wake me up only when the data is ready."_

You need three things to make this work:

1. A `std::mutex` (to protect the shared data).
2. A **`std::unique_lock`** (they do not work with `lock_guard`).
3. A `std::condition_variable`.

---
### 3. Wait and Notify


```cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> dataQueue; // The shared resource

void consumer() {
    // 1. We MUST use unique_lock
    std::unique_lock<std::mutex> lock(mtx);
    
    std::cout << "Consumer: Going to sleep until data arrives...\n";
    
    // 2a. It checks the predicate
	//	If true, it passes to the next line
	//	Else it does 2 things atomically:
    //   a) Unlocks the mutex.
    //   b) Puts the thread to sleep.

	// 2b. When woken up, it tries to re-lock the mutex (but may have to wait due to other threads).
	// Now it checks the predicate again and same as above.

    cv.wait(lock, []{ return !dataQueue.empty(); });
    
    // 3. We only reach here if we were woken up AND the queue is not empty.
    // We safely own the lock right now.
    int data = dataQueue.front();
    dataQueue.pop();
    
    std::cout << "Consumer: Processed data " << data << "\n";
}

void producer() {
    std::this_thread::sleep_for(std::chrono::seconds(2)); // Simulate work
    
    {
        std::lock_guard<std::mutex> lock(mtx);
        dataQueue.push(42);
        std::cout << "Producer: Data created!\n";
    } // Unlock happens here
    
    // 4. The Signal
    // Wake up exactly ONE waiting thread.
    cv.notify_one(); 
}

int main() {
    std::thread c(consumer);
    std::thread p(producer);
    
    c.join();
    p.join();
}
```

Don't use a single condition_variable with same lock but different lambdas, because notify_one will wake up one thread and it may wake up the undesired one. notify_all works but why bother.

A single `std::condition_variable` can be used by multiple threads simultaneously, but **every single thread waiting on it must pass a lock wrapped around the EXACT SAME physical mutex object.**

### 4. The Lambda Predicate

Why do we pass a lambda function that checks if the queue is empty? Why not just `cv.wait(lock);`?


```cpp
std::unique_lock<std::mutex> lock(mtx);

// 1. Thread goes to sleep
cv.wait(lock); 

// 2. --- SPURIOUS WAKEUP HAPPENS ---
// The OS randomly wakes this thread up. No data was actually produced.

// Ideally it should wake up when i tell it to using notify.

// 3. Thread assumes it was woken up by a legitimate notify()
int data = queue.front(); // CRASH! The queue is actually empty.
```

Because of a hardware phenomenon called **Spurious Wakeups**.

Inside the OS scheduler, threads can occasionally be woken up by random system interruptions, even if `notify_one()`/`notify_all()` was never called.

This happens due to low-level hardware interruptions, POSIX signal handling, or artifacts of the OS thread scheduler. 

The OS does not guarantee that a thread only wakes up when you tell it to.

If you don't use the lambda, the thread wakes up, assumes data is ready, tries to read from an empty queue, and crashes.

When you provide the lambda, `cv.wait` operates like this under the hood:

```cpp
while (!predicate()) { // while dataQueue is empty
    wait(lock);        // go to sleep
}
```

If a spurious wakeup happens, the thread wakes up, checks the lambda, sees the queue is still empty, and immediately goes back to sleep. 

---
### 5. `notify_one()` vs `notify_all()`

- `notify_one()`: Wakes up a single waiting thread. Use this when one piece of data was added, and only one thread can process it (like a work queue).

- `notify_all()`: Wakes up EVERY thread currently waiting on that condition variable. Use this for state changes (e.g., "The application is shutting down, everybody wake up and exit").
