
### 1. The Cost of Mutexes (Why do we need lock-free?)

When you use a `std::mutex`, and Thread A has the lock, Thread B goes to sleep.
Putting a thread to sleep and waking it up is called a **Context Switch**.

The OS has to save all the CPU registers, flush caches, and load a different thread. This takes about **1 to 2 microseconds** (too much).

Lock-free programming guarantees that at least one thread is _always_ making progress, and no thread is ever put to sleep by the OS.

### 2. `std::atomic`

To bypass the OS, we use hardware-level instructions. C++ exposes these through **`std::atomic<T>`**.

```cpp
#include <atomic>
#include <iostream>

std::atomic<int> counter = 0;

void fastIncrement() {
    counter++; // Mathematically guaranteed to be thread-safe. No mutex needed.
}
```

**How does this work without a lock?**

When the compiler sees `std::atomic`, it stops generating standard read/write machine code. Instead, it generates a specialised CPU instruction (like `LOCK XADD` on x86 processors).

`std::atomic` protects read and write. It guarantees the Read will be clean (you won't read half a byte from one thread and half from another). It guarantees the Write will be clean.

But `++` is safe because the designers of C++ heavily overloaded the `++`, `--`, `+=`, and `-=` operators for `std::atomic`. When you type `balance += 10;`, the C++ compiler translates that into a specific hardware instruction (like `LOCK XADD` on Intel processors). This instruction physically locks the motherboard's memory bus. It does the Read, the Math, and the Write in **one single, unbreakable clock cycle**.


#### a. `.load()` and `.store()`  

```cpp
#include <atomic>
#include <iostream>

int main() {
    // Initialization
    std::atomic<int> count{0}; 

    // --- WRITE ---
    // Syntax: .store(desired_value, memory_order = std::memory_order_seq_cst)
    count.store(42); 

    // --- READ ---
    // Syntax: .load(memory_order = std::memory_order_seq_cst)
    int current_value = count.load(); 

    std::cout << "Value is: " << current_value << "\n";
    return 0;
}
```

#### b. Overloading

C++ overloads the assignment operator (`=`) for writing, and provides an implicit conversion operator for reading.


```cpp
#include <atomic>
#include <iostream>

int main() {
    std::atomic<int> count{0};

    // --- WRITE ---
    count = 42; // Calls count.store(42) under the hood

    // --- READ ---
    int current_value = count; // Implicitly calls count.load() under the hood

    std::cout << "Value is: " << current_value << "\n";
    return 0;
}
```

#### c. Read-Modify-Write (The real power of atomics)

Often, you need to read a value, change it, and write it back in one unbreakable hardware step. `load()` and `store()` cannot do this together safely. For that, you use these methods:

- **Exchange (Write and return the _old_ value):**

```cpp
int old_val = count.exchange(100); 
```

- **Fetch and Add / Subtract:**

```cpp
count.fetch_add(5); // Adds 5 atomically
count.fetch_sub(2); // Subtracts 2 atomically
 
// Operator overloads do the exact same thing:
count += 5;
count++;
```


- **Compare and Swap (CAS, elaborated below) **

```cpp
int expected = 100;
int desired = 200;
// If count == 100, change it to 200. 
// Otherwise, update 'expected' to the real value.
bool success = count.compare_exchange_strong(expected, desired);
```

### 3. Compare-And-Swap (CAS)

You cannot use `std::atomic` like a normal variable for complex math.


```cpp
std::atomic<int> balance = 100;

// FATAL FLAW: 
// 1. Thread A reads balance (100).
// 2. Thread B reads balance (100), adds 50, writes 150.
// 3. Thread A adds 10, writes 110. (Thread B's update is lost).
balance = balance + 10; 
```

To fix this without a mutex, all lock-free programming relies on a single hardware instruction called **Compare-And-Swap (CAS)**. In C++, this is called **`compare_exchange_weak`** (or `strong` (for ARM, a very long story)).

1. **Look** at the shared variable.
2. **Remember** what you saw (the `expected` value).
3. **Calculate** the new value (the `desired` value).
4. **The Swap:** Ask the CPU to overwrite the shared variable with the `desired` value, **BUT ONLY IF** the shared variable still matches your `expected` value.
5. If someone else changed it while you were doing the math, the CPU refuses to write. The swap fails, and the CPU updates your `expected` value to whatever the new reality is.

---
### 4. The Lock-Free Loop

Because a CAS operation can fail (if another thread beat you to the punch), you must put it inside a `while` loop.


```cpp
#include <atomic>

std::atomic<int> shared_balance = 100;

void lockFreeAdd(int amount) {
    // 1. Read the current state
    int expected = shared_balance.load(); 
    int desired;

    // 2. The CAS Loop
    do {
        // Calculate what we want the new value to be
        desired = expected + amount; 

        // 3. The Hardware Swap
        // If shared_balance == expected:
        //    -> shared_balance = desired. Returns TRUE (loop breaks).
        // If shared_balance != expected:
        //    -> expected = shared_balance. Returns FALSE (loop repeats).
    } while (!shared_balance.compare_exchange_weak(expected, desired));
}
```

Even if Thread A fails the CAS because Thread B beat it, Thread A does not go to sleep. It instantly loops, recalculates, and tries again. This takes nanoseconds, completely bypassing the OS scheduler.

Compressed version doing the same thing:

```cpp
void lockFreeAdd(int amount) {
    int expected = shared_balance.load();
    while (!shared_balance.compare_exchange_weak(expected, expected + amount)) {
	    // Empty
    }
}
```

### 5. Memory Models (`memory_order`)

To make your code run fast, both the C++ Compiler (when building your `.exe`) and the physical CPU (when running the `.exe`) will aggressively rearrange your code. If two lines of code do not depend on each other, the CPU will execute them simultaneously, or swap their order entirely to keep its hardware pipelines full.

If you look at professional C++ code, you rarely see `.load()` or `compare_exchange_weak()` by themselves. You usually see:

```cpp
shared_balance.compare_exchange_weak(expected, desired, std::memory_order_release, std::memory_order_relaxed);
```

By default, C++ atomics use `std::memory_order_seq_cst` (Sequential Consistency). This mathematically guarantees that no thread will ever see instructions executed out of order.

However, enforcing this strict order requires the CPU to flush its hardware caches constantly, which degrades performance.

To get the absolute maximum speed out of a processor, lock-free programmers use **Relaxed Memory Models** (`memory_order_acquire`, `memory_order_release`, `memory_order_relaxed`).

These allow the compiler and the actual silicon CPU to rearrange the order of your compiled instructions to run faster, while still guaranteeing that specific mathematical relationships remain intact across threads.

Why `std::memory_order_seq_cst` is default? 

```cpp
int payload = 0;
std::atomic<bool> ready = false;

// --- THREAD 1 (Producer) ---
void producer() {
    payload = 42;          // Line A
    ready = true;          // Line B
}

// --- THREAD 2 (Consumer) ---
void consumer() {
    while (!ready) {}      // Line C (Spin until ready is true)
    std::cout << payload;  // Line D
}
```

The CPU looks at Thread 1 and says: `payload` and `ready` are completely different variables in memory. I'm going to write `ready = true` FIRST because that memory address happens to be closer to my cache, and I'll write `payload = 42` a microsecond later."

**Result:** Thread 1 sets `ready = true`. Thread 2 instantly wakes up, passes Line C, and reads `payload`. But Thread 1 hasn't actually written `42` yet! Thread 2 prints garbage. 

Your lock-free code has failed.

### Memory Barriers (The `std::memory_order`)

This is why Memory Models exist. A memory model is a **contract** you sign with the compiler and the CPU. It allows you to place invisible "fences" or "barriers" in your code, explicitly forbidding them from reordering instructions across that boundary.

When you use an atomic variable, you can pass a `std::memory_order` flag to dictate exactly how strict the chronological rules should be.

Here are the 3 tiers of memory models, from safest to fastest.

#### Tier 1: `memory_order_seq_cst` (default)

- **What it means:** Do everything exactly in the order I wrote it.

- **How it works:** It places a full, impenetrable hardware barrier before and after the operation. No instructions can be moved above it, and none can be moved below it. All threads are guaranteed to see the exact same chronological timeline of events.

- **The Catch:** This is the default in C++ (if you just type `ready = true;`), but it is the slowest. It forces the CPU to constantly flush its caches and wait.

#### Tier 2: `memory_order_acquire` & `memory_order_release` 

This is what professionals use to get maximum speed while staying safe. It creates a "half-barrier".

- **Release (Used on Writes):** "No code _before_ this line is allowed to be moved _after_ this line."
- **Acquire (Used on Reads):** "No code _after_ this line is allowed to be moved _before_ this line."
    

```cpp
// THREAD 1
payload = 42; 
// Memory Barrier! 'payload' MUST be written before 'ready' is set.
ready.store(true, std::memory_order_release); 

// THREAD 2
// Memory Barrier! 'payload' CANNOT be read until 'ready' is true.
while (!ready.load(std::memory_order_acquire)) {} 
std::cout << payload; // Mathematically guaranteed to be 42.
```

This is brilliant because it only enforces order exactly where it matters, letting the CPU reorder everything else in the background to maintain high speed.

#### Tier 3: `memory_order_relaxed`

- **What it means:** "I do not care about chronological order. I do not care what other variables are doing. Just guarantee that this _one specific variable_ is updated atomically without tearing."

- **How it works:** It places **zero** barriers. The CPU can reorder this instruction however it wants.

- **When to use it:** Only for simple counters (like `total_packets_sent++`) where no other data depends on the counter being updated at a specific time.
