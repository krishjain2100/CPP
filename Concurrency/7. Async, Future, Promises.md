### The Problem
Think about a standard function: `int x = calculateStuff();`
**You can't** pass functions into threads that have a return value as `std::thread` ignores return values.

```cpp
// ERROR: std::thread ignores return values.
int x = std::thread(calculateStuff); 
```

To get a value out of a `std::thread`, you have to:

1. Create a shared variable.
2. Create a `std::mutex`.
3. Create a `std::condition_variable`.
4. Pass the shared variable into the thread by reference.
5. Lock the mutex inside the thread, write the value, unlock, and call `notify_one()`.
6. Lock the mutex in `main`, call `cv.wait()`, and finally read the variable.

That is a massive amount of boilerplate for a simple return value.

---
### The Solution: `std::async` and `std::future`

Task-based concurrency changes the philosophy. Instead of saying _"Create a thread and run this function,"_ you say _"Run this task in the background and give me a receipt so I can claim the result later."_ That "receipt" is called a **`std::future`**.

```cpp
#include <iostream>
#include <future>
#include <chrono>

int complexMath() {
    std::this_thread::sleep_for(std::chrono::seconds(2)); // Simulate heavy work
    return 42;
}

int main() {
    // 1. Launch the task. 
    // std::async immediately returns a 'future' object.
    std::future<int> result = std::async(std::launch::async, complexMath);

    std::cout << "Main thread is free to do other work right now...\n";

    // 2. Claim the result.
    // If the math is done, it returns instantly.
    // If the math is NOT done, .get() pauses the main thread and WAITS.
    int finalValue = result.get(); 

    std::cout << "The answer is: " << finalValue << "\n";
}
```

---
### Pros of `std::future`

#### 1. `.get()`

Notice there are no mutexes, no condition variables, and no `.join()` calls.

When you call `result.get()`, the standard library handles the synchronization perfectly. If the background thread is still running, `.get()` will block your current thread until the data is ready.

_(Note: You can only call `.get()` ONCE. After you extract the value, the future is emptied. If you call it twice, your program crashes)._

#### 2. Exception Propagation

If `complexMath()` throws an exception, the background thread catches it, stores it safely inside the `std::future` object, and shuts down the thread cleanly.

When you call `result.get()` in the main thread, **the exact same exception is re-thrown in the main thread.**


```cpp
std::future<int> badTask = std::async(std::launch::async, []() -> int {
    throw std::runtime_error("Divide by zero!");
});

try {
    int x = badTask.get(); // The exception explodes HERE, in the main thread.
} catch (const std::exception& e) {
    std::cout << "Caught safely in main: " << e.what() << "\n";
}
```

#### 3. Launch Policies

The first argument to `std::async` is the launch policy. You have two choices:

- `std::launch::async`: Forces the OS to spawn a brand new, dedicated background thread immediately.

- `std::launch::deferred`: **Lazy evaluation.** It does _not_ spawn a thread. It waits until the exact moment you call `.get()`, and then runs the function synchronously on the main thread. (Useful if you only want to compute something if you end up actually needing it).

### The Catch

`std::async` delivers the value when the thread permanently dies.

### 1: The Early Delivery Scenario

Imagine you have a background thread that needs to do a massive initialisation (allocate memory, open a network port) which takes 2 seconds. Once the port is open, the main thread needs the port number immediately to tell the UI it's ready. But the background thread _also_ needs to stay alive to actually listen to that port for the next 10 minutes.

**Why `std::async` fails:** `std::async` relies on the `return` statement. If you return the port number, the function ends, and the thread is destroyed. You cannot return a value and keep the thread running.

`std::promise` decouples the delivery of the data from the death of the thread.


```cpp
void networkThread(std::promise<int> prom) {
    // 1. Heavy initialization (Takes 2 seconds)
    int port = openNetworkPort(); 

    // 2. Deliver the data to the main thread EARLY
    prom.set_value(port); 
    
    // 3. The thread keeps running! 
    // It does not return. It enters a 10-minute listening loop.
    listenForConnections(port); 
}
```

Because of `prom.set_value()`, the main thread's `future.get()` unblocks at exactly the 2-second mark, while the background thread  continues its loop.

### 2: Thread Pools

`std::async` forces you to spawn a brand new thread (or let the OS manage it). Spawning a new thread for every task is way too slow. Instead, professionals use a **Thread Pool**: a group of 4 or 8 threads created at the very start of the program that just sit in infinite loops waiting for jobs.

You cannot use `std::async` with a Thread Pool because `async` tries to manage the thread creation itself. 

So you create a `promise`, extract its `future`, and toss the `promise` into the existing Thread Pool queue along with your data.


```cpp
// 1. Create the channel
std::promise<int> prom;
std::future<int> fut = prom.get_future();

// 2. Give the promise to an ALREADY RUNNING thread in your pool
myThreadPool.submitJob([p = std::move(prom)]() mutable {
    int result = heavyMath();
    p.set_value(result); // Thread pool worker sends the result back
});

// 3. Main thread waits
int answer = fut.get();
```

### Another example for clarity

```cpp
#include <iostream>
#include <thread>
#include <future>
#include <chrono>

// The thread function takes the promise by value (using std::move)
void backgroundWorker(std::promise<int> prom) {
    std::cout << "Worker: Calculating...\n";
    std::this_thread::sleep_for(std::chrono::seconds(2));
    
    // 4. Push the data into the channel
    prom.set_value(42); 
    
    // Notice: The thread DOES NOT END HERE. 
    // It can keep doing other work even after sending the value!
    std::cout << "Worker: Value sent! Now doing cleanup work...\n";
    std::this_thread::sleep_for(std::chrono::seconds(1));
}

int main() {
    // 1. Create the Promise (Sender)
    std::promise<int> myPromise;
    
    // 2. Extract the Future (Receiver)
    std::future<int> myFuture = myPromise.get_future();
    
    // 3. Spawn a raw thread and MOVE the promise into it
    // We must use std::move because promises cannot be copied.
    std::jthread t(backgroundWorker, std::move(myPromise));
    
    std::cout << "Main: Waiting for data...\n";
    
    // 5. Block and wait for the thread to call set_value()
    int result = myFuture.get(); 
    
    std::cout << "Main: Received data -> " << result << "\n";
    
} // jthread automatically joins here
```


Just like setting a value, a background thread can manually catch an exception and shove it down the channel using `set_exception()`.


```cpp
void riskyWorker(std::promise<int> prom) {
    try {
        // Something goes wrong
        throw std::runtime_error("Database connection failed");
    } catch (...) {
        // Catch the current exception and push it into the promise
        prom.set_exception(std::current_exception());
    }
}
```

When the main thread calls `myFuture.get()`, that exact `runtime_error` will explode in the main thread, allowing you to catch it safely without crashing the whole program.

### `std::packaged_task<>`

Normally, if you want to run a function in a background thread and get a return value, you have to write a ton of manual boilerplate: create a `std::promise`, extract the `std::future`, write a `try-catch` block inside the worker function, and call `set_value()` or `set_exception()` manually.

`std::packaged_task<>` is a template wrapper that completely automates this entire process. It packages two distinct things into a single object:

1. **A Callable:** The actual function, lambda, or functor you want to execute.
2. **An Internal Promise:** A hidden `std::promise` that captures the function's return value or any thrown exceptions automatically.

The template argument for `std::packaged_task` is not a raw type (like `int` or `string`); it is a **Function Signature** matching the target callable: `std::packaged_task<ReturnType(ParameterTypes)>`.

Here is how you wire it up manually in a single-threaded context to see how it moves data:

```cpp
#include <iostream>
#include <future>

int addNumbers(int a, int b) {
    return a + b;
}

int main() {
    // 1. Wrap the function signature: takes two ints, returns an int
    std::packaged_task<int(int, int)> task(addNumbers);

    // 2. Extract the future (the receipt) BEFORE running the task
    std::future<int> resultFut = task.get_future();

    // 3. Execute the task manually like a normal function
    // This runs addNumbers, catches the return value, and slams it into the hidden promise
    task(10, 20); 

    // 4. Claim the result
    int final_sum = resultFut.get();
    std::cout << "The sum is: " << final_sum << "\n"; // Prints 30
```

- **Rule 1: It is Move-Only (`std::move`)** A `std::packaged_task` uniquely owns its internal asynchronous shared state. Therefore, it **cannot be copied**. If you want to hand a task over to another thread or push it into a vector/queue, you must explicitly transfer ownership using `std::move()`.

- **Rule 2: Executing it Clears the State** You can only invoke a `std::packaged_task` **once**. If you try to execute `task()` a second time, it will throw a `std::future_error` exception with a broken promise code.

- **Rule 3: Exception Routing is Built-In** If the function wrapped inside the `packaged_task` throws an exception, the task intercepts it, packages it, and delivers it to the future. The background thread will _not_ crash; instead, the exception is re-thrown the moment someone calls `.get()` on the associated future.
