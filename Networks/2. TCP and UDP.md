
There are two different mathematical philosophies for sending data: **TCP** and **UDP**:
## 1. TCP (Transmission Control Protocol)
If an application uses TCP, it is asking the Operating System to act as a highly protective supervisor. The OS guarantees that every single byte sent will arrive perfectly intact and in the exact order it was sent.
### Mechanism

- **The 3-Way Handshake: Before a single byte of payload is sent, the sender and receiver must formally agree to open a connection.
	1. **SYN:** Sender asks to synchronise sequence numbers.
    2. **SYN-ACK:** Receiver acknowledges and sends its own sequence number.
    3. **ACK:** Sender acknowledges the receiver's number. Then the connection considered "Established."
- **Sequence Numbers (Ordering):** TCP treats data as a continuous, numbered stream of bytes. It stamps every outgoing packet with a sequence number. If the receiving OS gets packet #5 before packet #4, it holds #5 in a hidden buffer and refuses to hand it to the application until #4 arrives, guaranteeing perfect order.

Now you might wonder what is the meaning of synchronizing sequence numbers:
The sender doesn't label the packets starting from 1, it starts at a randomly generated number. To tell this starting number to the other side of connection is synchronizing sequence numbers
Reasons for randomly generated sequence numbers: 
1. Security: So hackers can't intrude by sending their own packets, they can always send a 1 numbered packet to intrude the connection and corrupt the data. So this makes it safer from intrusion
2. The internet is messy, and sometimes network routers accidentally trap packets and delay them for minutes. Imagine you finish downloading an image and close the connection, but a router somewhere is still holding onto a delayed packet `#500` from that image. If your _new_ connection also started at `1`, that delayed packet might eventually arrive right when your new connection is expecting its own packet `#500`. Your OS would blindly glue the old image data into your new file, permanently corrupting it. By starting the new connection at a totally different random number (like `800,000`), when that old packet `#500` finally arrives, your OS instantly recognizes it as garbage and throws it in the trash.

You might also wonder how the old connection closed if the receiver didn't receive the #500 packet: The sender gets the signal that the packet it sent is lost somewhere so it resends it and this time it reaches and some time later the connection is closed, but actually the old packet was stuck in traffic, and the stuck packet reaches as a ghost packet after closing of connection.

You might also wonder that the ghost data problem isn't fully solved now. because still collisions might happen between packet numbering ranges between two connections. You are correct, this just reduces the probability but still there's a good probability of collisions and that probability is reduced more by some other means we won't be going through

### Acknowledgments and Retransmission (Reliability): 
In the world of TCP, the Operating System is incredibly paranoid about data getting lost. Whenever a computer successfully receives a packet of data, it is strictly obligated to send an ACK packet back to the original sender to prove the data arrived safely. 

An ACK packet doesn't just say "I got it!" Instead, it uses the **Acknowledgment Number** field in the TCP header to tell the sender exactly what it is expecting _next_.
Here is exactly how it works under the hood:
#### 1. The "Next Expected" Number
- If your computer receives a 100-byte packet starting at Sequence Number `5000`, it has successfully received bytes `5000` through `5099`.
- Your computer will instantly send an ACK packet back to the server stamped with Acknowledgment Number **`5100`**.
- This translates to: _"I have perfectly received everything up to 5099. I am now waiting for byte 5100."_
#### 2. Stopping the Clock
The primary purpose of the ACK packet is to stop the sender's **Retransmission Timer**. The moment a sender fires a packet onto the internet, it starts a stopwatch. If the sender does not receive an ACK packet before that stopwatch hits zero, it assumes the original packet was destroyed by a router, and it forcefully resends a clone of the data.
#### 3. Piggybacking (No Empty Envelopes)
While you _can_ send an empty packet that contains absolutely nothing but an ACK receipt, the OS avoids this because it clogs up the network. Because TCP is Full-Duplex (both sides talk at the same time), the OS usually just uses **Piggybacking**. It takes the ACK receipt and simply "staples" it to the header of the next packet of actual data it was planning to send back to the other computer anyway.

---
- **Flow Control (Sliding Window):** If a fast server is sending data to a slow smartphone, the phone's memory will quickly overflow. The phone's OS continuously sends a "Window Size" metric back to the server, dictating exactly how many bytes the server is allowed to send before pausing. This prevents the sender from overwhelming the receiver.

- **The Cost:** To achieve this perfection, TCP requires a massive amount of OS memory to track timers and states, and adds a heavy **20-byte minimum header** to every single packet. So it is a heavy cost process

**Ideal Use Cases:** Web Browsing (HTTP), Email (SMTP), File Transfers (FTP). Anything where a single missing or flipped byte corrupts the entire file.

### Role of OS
The Operating System must treat every single TCP connection as an independent entity.
For every single connection, the OS allocates a massive block of kernel memory to track its current **State** (where it is in its lifecycle) and its **Timers** (countdown clocks for failure detection).
##### 1. The States
A connection can only ever be in one exact state at any given microsecond. The OS tracks this so it knows exactly how to react to incoming packets.

1. **The Setup States:**
	- **`LISTEN`:** The OS is passively waiting for a new client to say hello.
	- **`SYN_SENT`:** The OS sent the first handshake packet and is waiting for a reply.    
	- **`SYN_RCVD`:** The OS received a hello, replied, and is waiting for the final handshake confirmation. 

2. **The Golden State:**
	- **`ESTABLISHED`:** The handshake is completely finished. This is the only state where actual application data (like a web page or a file) is allowed to flow.

3. **The Teardown States:** 
	Closing a connection requires a 4-way handshake (each side must independently say goodbye and acknowledge the other's goodbye).
	
	**Step 1: `FIN_WAIT_1`**
	- The Client's application calls `close()`.
	- The Client's OS Kernel generates a TCP **`FIN` (Finish)** packet and fires it at your Server.
	- The Client's OS shifts this connection to  **`FIN_WAIT_1`** state. This means: _"I have sent my goodbye, and I am waiting for the Server to acknowledge it."_
	
	**Step 2: `CLOSE_WAIT` 
	- The Kernel(Server) sees the `FIN` flag. It instantly replies with an **`ACK`** (Acknowledge) packet and shifts the connection into the **`CLOSE_WAIT`** state.
	- **The Client receives the `ACK` and shifts to `FIN_WAIT_2`**.
	When your Server's OS enters **`CLOSE_WAIT`**, The Client cannot send any more data.
	
	When the Kernel receives that `FIN` packet, makes your next `recv()` call return exactly `0` bytes. That `0` is the Kernel saying to C++ code: _"Finish whatever math you are doing, and officially close this socket."_

	**Step 3: `LAST_ACK`**
	- Your C++ code sees `recv()` returned `0`, so it executes the command: `close(client_fd)`.
	- The Server's OS Kernel generate its own **`FIN`** packet and send it to the Client.
	- The Server's OS shifts the connection to **`LAST_ACK`**. This means: _"My C++ application is finally done. I sent my goodbye, and I am waiting for the Client to acknowledge it."_
	
	**Step 4: The Final Deletion**
	- The Client receives your Server's `FIN` packet and replies with a final **`ACK`**.
	- The Server's OS receives the `ACK`. The 4-way handshake is complete.
	- The Server's OS completely obliterates the socket, deletes the Receive and Send buffers from RAM, and frees up the File Descriptor integer. The connection is officially **CLOSED**.
	- Whoever sent the first FIN packet (client here) drops into the `TIME_WAIT` state.
	
	**`TIME_WAIT`:** After a connection is successfully closed, the OS intentionally keeps the connection's memory alive in the `TIME_WAIT` state for **60 to 120 seconds**. If a router  delayed a stray packet(ghost packet, we talked about this above) from this closed connection, and it randomly arrives 30 seconds later, the OS needs to remember the connection so it can safely discard the ghost packet. If it deleted the memory immediately, a brand new connection might reuse that exact same port, and the ghost packet would corrupt the new connection's data.

##### 2. The Timers 
For every connection in the `ESTABLISHED` state, the OS must constantly update and monitor multiple countdown timers.

1. **The Retransmission Timer
	- **The Logic:** Every time the OS sends a packet, it starts a stopwatch. If the OS does not receive an `ACK` from the receiver before the stopwatch hits zero, it assumes the packet was dropped and re-transmits it.
	- The OS cannot use a hardcoded timer, because one client might be in the same city, and another might be on a satellite in orbit. The OS uses a complex algorithm (Jacobson's Algorithm) to constantly calculate the **Round Trip Time (RTT)** for every individual packet, dynamically adjusting the timer for every single connection on the fly.

2. **The Keep-Alive Timer**
	- **The Logic:** If a client connects to a server, but neither side sends any data for hours, how does the server know the client didn't just lose power?
	- **The Action:** The OS maintains a Keep-Alive timer (usually set to 2 hours). If the timer hits zero, the OS automatically sends an invisible, empty "probe" packet. If the client's OS replies, the timer resets. If it doesn't, the OS kills the connection and frees the memory.

3. **The Persist Timer
	- **The Logic:** Flow control dictates that if the receiver's RAM is completely full, it sends a packet saying: _"Window Size: 0"_ (Meaning: Stop sending, I am full). The sender immediately stops.
	- **The Action:** But what if the receiver later sends a packet saying _"Window Size: 500"_ to resume the flow, and that packet gets dropped by a router? The sender would wait forever, and the receiver would wait forever. To prevent this deadlock, the sender starts a Persist Timer. When it expires, it sends a tiny 1-byte probe asking, _"Do you have space yet?"_

## 2. UDP (User Datagram Protocol)
It fires the data out onto the network and instantly forgets about it. It offers absolutely no guarantees.
### Mechanism
- **No Handshake:** The sender simply addresses the packet and pushes it to the hardware immediately.
- **No Reliability:** If a router drops the packet, or it gets corrupted by electrical interference, it is gone forever. The sender will never know, and the receiver will never ask for it again.
- **No Ordering:** If you send Packet A then Packet B, they might take different physical routes across the globe. The receiver might get Packet B first. It hands them to the application exactly as they arrive.
- **Discrete Message Boundaries:** Unlike TCP (which is a continuous, blending stream of bytes), UDP maintains strict message boundaries. If you send a 500-byte chunk, the receiver will get exactly one 500-byte chunk.
- **The Benefit:** Because it tracks nothing, UDP requires almost zero OS memory, has zero latency overhead from handshakes, and uses a microscopic **8-byte header**.

**Ideal Use Cases:** 
* **Zoom:** If a frame of video is dropped, you don't want the OS to pause the call and wait for a retransmission, you just want to skip it and play the newest frame. "Late data is useless data."
- **Multiplayer Gaming:** Player position coordinates update 60 times a second. Missing one update doesn't matter because a newer one is already arriving.
