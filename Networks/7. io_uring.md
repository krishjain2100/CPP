For 20 years, `epoll` was the standard of high-performance Linux networking. 
It powered Node.js, Nginx, Redis, etc. 
But as hardware got faster, especially with the invention of SSDs (solid state drive) and 100Gbps network cards, engineers realised `epoll` had limitations.

---
### The Problem: Context Switches through System Calls

Think about the `epoll` event loop. Even though it is non-blocking, the CPU has to cross the physical memory boundary between **User Space** (your C++ program) and **Kernel Space** (the OS) ( context-switch ) a lot of times.

1. Call `epoll_wait()` -> **Context Switch** (Kernel checks the watchlist).
2. Call `accept()` -> **Context Switch** (Kernel fetches the new client).
3. Call `recv()` -> **Context Switch** (Kernel copies data to your buffer).
4. Call `send()` -> **Context Switch** (Kernel copies data to the NIC buffer).

---
### Readiness vs. Completion

To fix it, Jens Axboe (a Linux kernel developer) introduced **`io_uring`** in 2019. 
It completely rewrote the rules of how C++ programs talk to the Operating System.

`epoll` is a **Readiness** model.

It tells you: "_FD 5 is ready and it has data in its buffer._"
But `epoll` does not do the actual work. You still have to manually call `recv()` and drag the bytes across the User/Kernel boundary yourself.

`io_uring` is a **Completion** model.

- It tells you: _"I read FD 5 and I put the bytes into your C++ array. It is completely done."_
- You never call `recv()`. You never call `send()`. The Kernel does the heavy lifting asynchronously in the background.

---
### The Architecture: Ring Buffers and Shared Memory

To eliminate system calls, `io_uring` uses **Shared Memory (`mmap`)**.

When you start an `io_uring` server, your C++ program asks the OS to allocate two circular arrays (Ring Buffers) in RAM, and then _removes the security wall between them_. 

Both the C++ program and the OS Kernel can read and write to these two queues simultaneously without requiring any context switches.

#### 1. The Submission Queue (SQ)

You fill out Work Orders called **SQEs** (Submission Queue Entries) instead of calling functions.

- You write: _"Hey Kernel, accept a connection on FD 3"_ or _"Hey Kernel, read 1024 bytes from FD 4 into this C++ memory pointer."_
- You drop this Work Order into the SQ.

#### 2. The Completion Queue (CQ)

When the Kernel finishes a Work Order, it creates a receipt called a **CQE** (Completion Queue Entry).

- The Kernel drops the receipt into the CQ.
- The receipt says: _"Job done. I read 1024 bytes. No errors."_

```cpp
   struct io_uring { 
	   struct io_uring_sq sq; // 1. The Submission Queue (Outbox) State 
	   struct io_uring_cq cq; // 2. The Completion Queue (Inbox) State 
	   unsigned int flags; // 3. Configuration flags (e.g., SQPOLL) 
	   int ring_fd; // 4. The underlying file descriptor for the ring itself unsigned 
	   int features; // 5. Supported kernel feature flags 
	   int enter_ring_fd; // 6. Multiplexed descriptor for virtualization/internal use 
	   __u32 pad[3]; // 7. Padding bytes for memory alignment 
   };
```

```cpp
struct io_uring_sqe {
```

```cpp
void io_uring_prep_accept(struct io_uring_sqe *sqe, int fd, struct sockaddr *addr, socklen_t *addrlen, int flags);
// fills the sqe with the relevant data to place a accept work order
// fd-receptionist fd
```

If you are wondering how does the tail pointer of sq work, there are two tail pointer, one is local to cpp program and one shared by the kernel and program, when get is called the local pointer only gets updated, but when we call submit and wait that is when the shared tail pointer gets updated to the local pointer
```cpp
int io_uring_submit_and_wait(struct io_uring *ring, unsigned want_events);
// want_events: minimum number of events completed before the program is woke up
// returns number of events completed by the time program is woke up
```

```cpp
struct io_uring_cqe { 
__u64 user_data; /* sqe->user_data submission passed back */ 
__s32 res; /* result code for this event:The return value we would get if the operation was performed normally(like client_fd in accept() etc.) */
__u32 flags; /* metadata flags regarding the completion */ 
};
```
You can notice that cqe is only 16bytes, while sqe was 64bytes, also you can notice that size of cq would be half that of sq but it can still hold double the number of orders than sq

### Complete Server

```cpp
#include <iostream>
#include <liburing.h>     // The official io_uring wrapper
#include <sys/socket.h>
#include <netinet/in.h>
#include <unistd.h>
#include <cstring>
#include <cstdlib>

// ---------------------------------------------------------
// 1. The State Machine (Context)
// ---------------------------------------------------------
// We must attach one of these conninfo to every Work Order (SQE) so we know 
// what to do when the Kernel gives us the Receipt (CQE).
enum EventType { ACCEPT, READ, WRITE };

struct ConnInfo {
    int fd;
    EventType type;
    char buffer[1024];
};

// Helper function to create a Work Order to ACCEPT a new user
void add_accept_request(struct io_uring *ring, int server_fd, sockaddr_in *client_addr, socklen_t *client_len) {
    struct io_uring_sqe *sqe = io_uring_get_sqe(ring);
    
    io_uring_prep_accept(sqe, server_fd, (struct sockaddr*)client_addr, client_len, 0); // sets all fields of sqe to accept a new client
    
    // Create the context ticket and attach it to the Work Order
    ConnInfo *info = new ConnInfo{server_fd, ACCEPT};
    io_uring_sqe_set_data(sqe, info); //pointer 'info' is stored in user_data field in sqe
}

// Helper function to create a Work Order to READ data
void add_read_request(struct io_uring *ring, int client_fd) {
    struct io_uring_sqe *sqe = io_uring_get_sqe(ring);
    
    ConnInfo *info = new ConnInfo{client_fd, READ};
    
    io_uring_prep_recv(sqe, client_fd, info->buffer, sizeof(info->buffer), 0);
    io_uring_sqe_set_data(sqe, info);
}

// Helper function to create a Work Order to WRITE data
void add_write_request(struct io_uring *ring, ConnInfo *req, int bytes_to_send) {
    struct io_uring_sqe *sqe = io_uring_get_sqe(ring);
    
    req->type = WRITE; // Update state
    io_uring_prep_send(sqe, req->fd, req->buffer, bytes_to_send, 0);
    io_uring_sqe_set_data(sqe, req);
}

// ---------------------------------------------------------
// 2. The Main Server
// ---------------------------------------------------------
int main() {
    // A. Setup the standard Receptionist socket
    int server_fd = socket(AF_INET, SOCK_STREAM, 0);
    int opt = 1;
    setsockopt(server_fd, SOL_SOCKET, SO_REUSEPORT, &opt, sizeof(opt));

    sockaddr_in server_addr{};
    server_addr.sin_family = AF_INET;
    server_addr.sin_port = htons(8080);
    server_addr.sin_addr.s_addr = INADDR_ANY;

    bind(server_fd, (struct sockaddr*)&server_addr, sizeof(server_addr));
    listen(server_fd, 256);

    // B. Initialize the shared-memory io_uring (Queue size: 256)
    struct io_uring ring;
    io_uring_queue_init(256, &ring, 0); 
    std::cout << "io_uring Server listening on Port 8080...\n";

    // C. Kickstart the loop by asking the Kernel to accept the first user
    sockaddr_in client_addr;
    socklen_t client_len = sizeof(client_addr);
    add_accept_request(&ring, server_fd, &client_addr, &client_len);

    // ---------------------------------------------------------
    // 3. The io_uring Event Loop
    // ---------------------------------------------------------
    while (true) {
        // Submit all pending Work Orders and wait for at least 1 Receipt
        io_uring_submit_and_wait(&ring, 1);

        struct io_uring_cqe *cqe;
        unsigned head;
        unsigned count = 0;

        // Iterate through all Receipts the Kernel left in the Completion Queue
	    // the thing below is just a define statement and not a actual function it is just interpreted as a for loop
        io_uring_for_each_cqe(&ring, head, cqe) {
            ++count;

            // Extract our custom struct so we know what this receipt is for
            ConnInfo *req = (ConnInfo *)io_uring_cqe_get_data(cqe);

            // cqe->res holds the return value of the sys call (bytes read, or  
            // the new FD)
            int result = cqe->res; 

            if (req->type == ACCEPT) {
                if (result >= 0) {
                    std::cout << "Kernel accepted user! FD: " << result << "\n";
                    // 1. Issue a READ order for the brand new client
                    add_read_request(&ring, result);
                    // 2. Issue a new ACCEPT order so Receptionist keeps working
                    add_accept_request(&ring, server_fd, &client_addr, &client_len);
                }
                delete req; // Clean up memory

            } else if (req->type == READ) {
                if (result > 0) {
                    std::cout << "Kernel read " << result << " bytes!\n";
                    // Turn around & issue a WRITE order using the same buffer
                    add_write_request(&ring, req, result);
                } else {
                    // Result == 0 means client disconnected
                    std::cout << "Client disconnected.\n";
                    close(req->fd);
                    delete req;
                }

            } else if (req->type == WRITE) {
                // We successfully echoed the data. Issue a new READ order.
                add_read_request(&ring, req->fd);
                delete req;
            }
        }

    // Tell the Kernel we have processed these receipts so it can reuse the mem.
        io_uring_cqe_advance(&ring, count);
    }

    return 0;
}
```

---
### The Three Critical Takeaways

1. **`io_uring_prep_*` Functions:** Notice how we don't call `accept()`, `recv()`, or `send()`. We call `prep_accept()`, `prep_recv()`, etc. We are just writing down instructions on a piece of paper (the SQE).

2. **`io_uring_cqe_get_data`:** We attached `ConnInfo` to the request, and the Kernel filled it. 

3. **`cqe->res`:** This is the Receipt. If you asked for an `accept`, `res` is your brand new File Descriptor. If you asked for a `recv`, `res` is the number of bytes the Kernel placed into your buffer.
