**POSIX Socket API** is a standardised set of C functions that allows the program to talk to the kernel's network stack. 

---
Side note: An IP address is associated with every NIC so the system could have multiple IP addresses if using more than one NIC. Also new RX/TX rings are allocated per NIC.

### 1. `socket()` 

Before you can receive data, you must ask the OS Kernel to allocate memory for a new networking File Descriptor and a set of internal, private software buffers (queues) (the Send Buffer (SO_SNDBF) and Receive Buffer (SO_RCVBF))

```cpp
int server_fd = socket(int domain, int type, int protocol);
```

- **`domain`:** Tells the kernel which addressing family to use.
    - `AF_INET`: Use IPv4 (32-bit addresses).
    - `AF_INET6`: Use IPv6 (128-bit addresses).

- **`type`:** Tells the kernel what kind of state machine to attach to this socket.
    - `SOCK_STREAM`: Use TCP (Reliable, ordered, requires 3-way handshake).
    - `SOCK_DGRAM`: Use UDP (Fire-and-forget, no handshake, unordered).

- **`protocol`:** Usually set to `0` to let the OS automatically choose the default protocol for the given `type` (e.g., it will choose TCP for `SOCK_STREAM`).

- **Returns:** An integer (the File Descriptor, e.g., `3`). If it fails, it returns `-1`.

By separating `type` and `protocol`, the OS gives you a choice(skip this part if not interested)
- `socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)`: _"Kernel, I want to use TCP, and I want YOU to handle all the math. Just give me a clean stream of data."_
- `socket(AF_INET, SOCK_RAW, IPPROTO_TCP)`: _"Kernel, I want to use TCP, but step aside. I am building the raw 1s and 0s of the headers manually in my C++ code."_
You might wonder if `SOCK_RAW` means "step aside, I'm doing the TCP math," why do you still have to pass `IPPROTO_TCP` to the OS?
1. Outbound: The IP Header "Protocol" Field:
	When your C++ code mathematically generates a raw TCP header and a payload, you hand that chunk of bytes to the OS to send over the internet.
	Because you used `socket(AF_INET, ...)`, the OS is still responsible for wrapping your raw chunk inside an **IPv4 Header** before firing it out of the network card.
	Every IPv4 header has a mandatory 8-bit field called the `Protocol` field. This field tells the receiving computer what kind of data is hidden inside the IP packet.
2. Inbound: The Kernel's Bouncer (Filtering)
	This is the most important reason. A server might receive 100,000 packets a second from the internet.
	When a packet arrives, the OS strips off the Ethernet and IP headers. If you have a raw socket open, the OS needs to know if it should hand a copy of that raw packet to your C++ program.
	- If you just said "Give me a raw socket," the OS would have to copy _every single packet_ hitting the machine (TCP, UDP, ICMP ping packets, routing updates) and dump them all into your C++ program. Your program would instantly crash from memory exhaustion.
	- By specifying `IPPROTO_TCP`, you are giving the OS a strict filtering rule. You are saying: _"Only wake up my raw socket if the incoming IP header specifically says it contains TCP data. Ignore the UDP and Ping traffic."_
If you are wondering, are all TCP packets coming to the server sent to our program in SOCK_RAW, even if their port number doesn't match our program: YES
And if you are also wondering, then would the programs for which the packet was actually meant for get the packet: YES the OS will create a photocopy of it to send to our program

### 2. `bind()`

You have a socket, but the OS doesn't know what traffic to send to it. `bind()` tells the kernel: _"Any packet that arrives at the NIC destined for Port 8080 belongs to File Descriptor 3."_

```cpp
int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```

- **`sockfd`:** The file descriptor you just got from `socket()`.
- **`addr`:** A pointer to a C-struct (`sockaddr_in`) containing two critical pieces of information:
    - **IP Address:** Usually set to `INADDR_ANY` (0.0.0.0), meaning the socket will accept packets from any physical NIC on the motherboard.
    - **Port:** The 16-bit port number (e.g., `8080`). _Note: You must use `htons(8080)` to convert the number into Big-Endian format, which is the mathematical standard the internet uses._
    8080 is 1F 90 in standard hexadecimal, computer stores it as 2 bytes, 90 goes in smaller mem addr and 1F in bigger one (Little endian) so that addition could go from LSB to MSB easily, but humans read it left to right so Big Endian is used to transfer data i.e, 1F is sent first then 90.
- **`addrlen`:** The size of the `addr` struct in bytes (usually `sizeof(addr)`).

Might want to hold off any questions till accept().

### 3. `listen()`

This function flips the kernel's TCP state machine from `CLOSED` to `LISTEN`. Now the socket will start accepting connections.

```cpp
int listen(int sockfd, int backlog);
```

- **`sockfd`:** Your server's file descriptor.

- **`backlog`:** This is a crucial security and performance parameter. It tells the OS exactly how many incoming connections it is allowed to hold in the **SYN-Backlog Queue** before it starts rejecting/dropping new `SYN` packets. The (N+1)th simultaneous connection attempt is immediately dropped by the hardware.
---
What we setup above was a listening socket, think of it like the **receptionist** of our program, 
it only handles the handshake with new connections, whatever happens after that happens on the connection socket, that is created using accept() we will study after this.
The point of connected socket is to handle many different clients, so that the data from each client remain segregated because in tcp only the final data is given to the program and it has no way of telling who sent it.
Listening socket is identified by a 2-tuple hash(Destination IP+Destination Port)
Connected socket is identified by a 4-tuple hash(Source IP+Source Port+Destination IP+Destination Port)
#### 1. The Listening Socket (2-Tuple)
When you call `bind()` and `listen()` on File Descriptor 3, you create a Listening Socket. Think of this socket as the **Receptionist**. The Receptionist uses a **2-Tuple** (Local IP + Local Port). Its only job is to intercept packets that are trying to start a _brand new_ connection (TCP `SYN` packets).

We will see what happens when both Alice and Bob establish connection to the server at the same time.
#### 2. The Connected Sockets (4-Tuple) 
When Alice's `SYN` packet hits Port 80, the Receptionist (FD 3) handles the 3-way handshake. When the handshake finishes, your C++ code calls `accept()`. (If accept() is not called the accept queue( mentioned in next section) will just keep filling till full, and connections after that will fail)

At this exact moment, the OS Kernel creates a **Brand New Socket** (e.g., FD 4) just for Alice. To ensure Alice's future data goes to FD 4 and _not_ the Receptionist (FD 3), the kernel records Alice's **4-Tuple** in its internal hash table: `[Src IP: Alice's IP, Src Port: 55000, Dst IP: Server IP, Dst Port: 80] -> Maps to FD 4`

When Bob connects a millisecond later, `accept()` creates FD 5. The kernel records Bob's 4-Tuple: `[Src IP: Bob's IP, Src Port: 61234, Dst IP: Server IP, Dst Port: 80] -> Maps to FD 5`

Now, both Alice and Bob start streaming data to Port 80 at the same time. Here is exactly what the OS Kernel does when a packet arrives:
1. **Read the Headers:** The kernel reads the incoming IP and TCP headers to extract the full 4-Tuple.
2. **Check for Established Connections (4-Tuple Match):** It hashes the 4-Tuple and checks its table. If it perfectly matches Alice's 4-Tuple, it drops the payload safely into FD 4's private buffer.
3. **Fallback to the Listener (2-Tuple Match):** What if a new user, Charlie, sends a `SYN` packet? The kernel hashes Charlie's 4-Tuple. It finds _no match_ because Charlie isn't connected yet. As a fallback, it drops the Source IP and Source Port, creates a 2-Tuple (just Dest IP and Dest Port 80), and checks the table again. It finds the Receptionist (FD 3) and hands the `SYN` packet to it to begin the handshake.

**Summary:** `bind()` only cares about the Destination Port because it is setting up the Receptionist. The 4-Tuple is required because it is the only mathematical way to uniquely identify 10,000 different clients who are all talking to the exact same Destination Port at the exact same time.

### 4. `accept()`

This is where your C++ thread goes to sleep. It tells the OS: _"Pause my program. Do not wake me up until a client has successfully completed the 3-way handshake and is sitting in the ESTABLISHED queue."
#### The Mechanics of the Sleep

There are 2 queues allocated for every receptionist socket.

1. **The Accept Queue:** A line for _Clients_ who have finished the 3-way handshake and are waiting for your C++ code to process them.
2. **The Wait Queue:** A line for _Threads_ waiting for work.

When your C++ thread calls `accept()` and the Accept Queue is empty, the OS Kernel physically removes your thread from the CPU's active schedule and drops it into the Receptionist socket's **Wait Queue**. Your thread is now in a `SLEEPING` state (0% CPU).

The microsecond a client finishes a 3-way handshake, the OS drops the client into the Accept Queue, looks at the Wait Queue, sees your C++ thread parked there, and wakes it up to handle the client. The socket is automatically created by the OS (we don't have to call the above functions again).

```cpp
int client_fd = accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
```

- **`sockfd`:** Your listening server file descriptor.

- **`addr`:** A pointer to an empty `sockaddr_in` struct. When the kernel wakes your program up, it fills this struct with the **Client's IP Address** and **Client's Port**, so you know exactly who connected to you.

- **`addrlen`:** A pointer to the size of the `addr` struct.

- **Returns:** A **BRAND NEW** File Descriptor (e.g., `4`).

The server socket (`3`) NEVER handles data. Its only job is to listen for connections. When a connection is established, OS gives you a new dedicated socket (`4`) just for that client, and the server socket (`3`) goes back to listening.

If you might be wondering, yes the accept() is run in a while loop so that we can keep handling new connections.

### 5. `recv()`

The hardware DMA'd the packet to RAM. The kernel stripped the Ethernet, IP, and TCP headers. The pure payload is sitting in Socket 4's receive buffer. `recv()` moves it into your C++ variables.

#### The Mechanics of the Sleep 

Just like the Receptionist socket has a Wait Queue for `accept()`, **every connected client socket has its own Wait Queue for `recv()`.** 
If you call `recv()` and the client's Receive Buffer is currently empty, the OS Kernel physically removes your thread from the CPU and drops it into this specific connected socket's Wait Queue. Your thread consumes 0% CPU until the hardware drops new payload data into the buffer, at which point the Kernel wakes your thread back up to read it.

```cpp
ssize_t recv(int sockfd, void *buf, size_t len, int flags);
```

- **`sockfd`:** The `client_fd` you got from `accept()`.

- **`buf`:** A pointer to a character array in your C++ code (e.g., `char buffer[1024];`).

- **`len`:** The maximum number of bytes you are willing to read (usually the size of your buffer, `1024`).

- **`flags`:** Usually `0`. (Can be used for special kernel instructions, like `MSG_PEEK` to look at the data without removing it from the kernel's buffer).

- **Returns:** The number of bytes actually read. If it returns `0`, it means the client gracefully disconnected (sent a `FIN` packet). If it returns `-1`, an error occurred.

`size_t` is unsigned and `ssize_t` is signed. 
`ssize_t` is used here to allow the return of `-1` for error code as in the POSIX standard, the universal error code is `-1`

`void` is used for `*buf` because the OS does not know what kind of data is being received and doesn't care too. A `void *` is a pointer stripped of all context.

You might wonder what happens if the client sends two different messages, will i receive them in a single recv call (assuming they both arrive before the thread is woken up): Yes the recv just puts all the data in the Rx buffer in your buffer address given, it is upto you to sort out what is a single message, typically the server and client already have a proper syntax to send data in a way that the server doesn't gets confused by these type of things.
The format or syntax of sending messages is already been agreed during the design phase of server and client, so that does not happen while a connection is being established.

Also if you are wondering, yes one message can also be received in two different recv() calls.

What happens if you call the recv() for only 10 bytes but there is 100 bytes sitting in the Rx buffer, the leftover 90 bytes will sit there patiently waiting for you to call the recv() again.

### 6. `send()`

Takes your C++ string and copies it from your application into this specific FD's Send Buffer. The Kernel's network stack reads the data from the private buffer and wraps it in TCP, IP, and Ethernet headers. The Kernel then drops this completed frame into TX Ring. The NIC's MAC chip performs a DMA pull, copying the frame from the TX Ring into the network card, where the PHY chip fires it out the wire.

```cpp
ssize_t send(int sockfd, const void *buf, size_t len, int flags);
```

- **`sockfd`:** The `client_fd`.

- **`buf`:** A pointer to the data you want to send (e.g., `"HTTP/1.1 200 OK"`).

- **`len`:** The exact number of bytes you are sending.

- **`flags`:** Usually `0`.

It returns the number of bytes accepted, if you send 1000 bytes and it returns 400, it means only first 400 bytes were sent its you responsibility to send the remaining 600 bytes.
If it returns -1, it means a error has occurred

### 7. `close()`


```cpp
int close(int fd);
```

- **`fd`:** The file descriptor to close.

- **The Action:** Calling this triggers the kernel to send a TCP `FIN` (Finish) packet to the client, perform the 4-way disconnect handshake, and physically delete this specific FD's private Receive and Send Buffers from system RAM, returning that memory to the OS.

### The Complete C++ TCP Server

```cpp
#include <iostream>
#include <sys/socket.h> // For socket(), bind(), listen(), accept(), send(), recv()
#include <netinet/in.h> // For sockaddr_in and INADDR_ANY
#include <unistd.h>     // For close()
#include <cstring>      // For memset()

int main() {
    // ---------------------------------------------------------
    // 1. socket() - The Receptionist
    // ---------------------------------------------------------
    int server_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (server_fd == -1) {
        std::cerr << "Failed to create socket.\n";
        return 1;
    }

    // ---------------------------------------------------------
    // 2. bind()
    // ---------------------------------------------------------
    struct sockaddr_in server_addr;
    memset(&server_addr, 0, sizeof(server_addr)); // Zero out the struct
    
    server_addr.sin_family = AF_INET;           // IPv4
    server_addr.sin_addr.s_addr = INADDR_ANY; // Listen on all network interfaces (0.0.0.0)
    server_addr.sin_port = htons(8080); // Convert Port 8080 to Big-Endian network bytes

    if (bind(server_fd, (struct sockaddr*)&server_addr, sizeof(server_addr)) == -1) {
        std::cerr << "Failed to bind to port 8080.\n";
        close(server_fd);
        return 1;
    }

    // ---------------------------------------------------------
    // 3. listen()
    // ---------------------------------------------------------
    // Tell the kernel to start accepting SYNs, with a backlog queue of 10.
    if (listen(server_fd, 10) == -1) {
        std::cerr << "Failed to listen.\n";
        close(server_fd);
        return 1;
    }
    
    std::cout << "Server is listening on port 8080...\n";

    // ---------------------------------------------------------
    // The Server Loop
    // ---------------------------------------------------------
    while (true) {
    
        // 4. accept() - The Blocking Handoff
        // The thread goes to sleep at accept() if the Established Queue is 
        // empty. It consumes 0% CPU until then.
        
        struct sockaddr_in client_addr;
        socklen_t client_len = sizeof(client_addr);
        
        int client_fd = accept(server_fd, (struct sockaddr*)&client_addr, &client_len);
        if (client_fd == -1) {
            std::cerr << "Failed to accept client.\n";
            continue;
        }
        
        // The 11th connection won't return -1, it will be as if the SYN packet
        // never came

        std::cout << "Client connected! Kernel gave us FD: " << client_fd << "\n";

        // 5. recv() - Bridging RAM to User Space
        // The thread goes to sleep here again, waiting for the client to send
        // payload data.
        char buffer[1024] = {0}; 
        // This is also blocking, it means that the control goes to OS and wakes this thread up when something is recieved.
        ssize_t bytes_read = recv(client_fd, (void*)buffer, sizeof(buffer), 0);

        if (bytes_read > 0) {
            std::cout << "Received " << bytes_read << " bytes: " << buffer << "\n";

            // 6. send()
            send(client_fd, (const void*)buffer, bytes_read, 0);
        }

        // 7. close()
        // We are done with this client. Send the FIN packet and delete the 
        // private buffers for FD 4.
        close(client_fd);
        std::cout << "Client disconnected. Receptionist is ready for the next client.\n\n";
    }

    // Shut down the main receptionist socket (unreachable in this infinite 
    // loop, but good practice).
    close(server_fd);
    return 0;
}
```


**Why we have seperate sockaddr_in and sockaddr ?**

```cpp
struct sockaddr {
    unsigned short sa_family;    // 2 bytes (The protocol type, e.g., AF_INET)
    char           sa_data[14];  // 14 bytes of raw, unformatted address data
};

struct sockaddr_in {
    short          sin_family; // 2 bytes (Must be set to AF_INET)
    unsigned short sin_port;   // 2 bytes (The Port Number, e.g., 8080)
    struct in_addr sin_addr;   // 4 bytes (The 32-bit IPv4 Address)
    char           sin_zero[8];// 8 bytes of pure PADDING (zeros)
};
```
sockaddr is the old type we used, in which we had to manually fill in the 14 bytes of data which was a cumbersome task, but sockaddr_in made it easier for us, the sin_zero in it is just so it matches the length of sockaddr and sockaddr_in can be typecasted in sockaddr because that is what our functions use

Why memset is used when we are filling the data anyways in sockaddr_in? To fill the padding of 8 bytes, it has to be filled with zeros so as to not confuse the os

Compile and Run. Open a new terminal and type `nc 127.0.0.1 8080`.
`127.0.0.1`  This is a special IPv4 address. When the OS Kernel sees this IP, it knows not to send the packet down to the physical Network Card. Instead, it performs a U-turn in software (RAM), instantly routing the packet straight back up to your own machine's network stack.

When you hit Enter, Netcat executes a microscopic, highly optimised C program.

1. Netcat instantly calls `socket()` and then calls a POSIX function: `connect()`.
	
	- This forces your OS Kernel to generate a TCP `SYN` packet and fire it at Port 8080.
	
	- Your C++ Server's Kernel receives it, finishes the 3-way handshake, and drops Netcat into the Accept Queue.
	
	- Your frozen C++ thread is violently woken up from `accept()`, prints _"Client connected!"_, and then goes right back to sleep on `recv()`.

2. Netcat then acts as a raw, transparent pipe between your keyboard and the network

	- When you type _"Hello"_ into the Netcat terminal and hit Enter, Netcat reads your keystrokes and immediately calls `send()`.
	
	- This pushes the text through the kernel, U-turns it tand drops it into your C++ Server's private Receive Buffer. 
	
	- Your server's `recv()` unblocks, reads the text, and prints it!

3. Because your C++ server then takes that text and uses `send()` to echo it right back, Netcat catches it. Netcat's internal `recv()` triggers, and it prints _"Hello"_ back out to your terminal screen.


**VERY IMPORTANT POINT:**
We can loosely say that the listener (receptionist) is working asynchronously. 
Because that single C++ line instructed the kernel and hardware to do all the work of raising and listening to interrupts, doing the 3-way handshake, figuring out where to route the data and filling the Established Queue for `accept()`.

**The C++ program was completely oblivious. It didn't pause its execution during the filling of the queue

### `memset()`

**`memset()`** stands for **Memory Set**. It is used to  fill a continuous block of RAM with a specific, repeating byte. It is used as a **Memory Wiper** to clear out "garbage" data before you start using a variable.

In languages like Python or Java, when you create a new variable, the language automatically clears the memory for you behind the scenes.

C and C++ prioritise absolute speed, so they **do not** clean up memory for you. 
```cpp
struct sockaddr_in server_addr;
```

The OS carves out 16 bytes of RAM for this struct. But those 16 bytes still contain whatever 1s and 0s happened to be left behind by the last program that used that exact physical spot in RAM. If we don't clean it, it will corrupt network data. When we hand it to the Kernel via `bind()`, the Kernel will try to read that garbage and crash.

To fix this, we use `memset()` to overwrite every single byte in that struct with exactly `0`.

```cpp
void *memset(void *ptr, int value, size_t num);
```

- **`ptr`:** A `void *` pointing to the starting memory address. It is a `void *` because `memset()` doesn't care if you are wiping a string, an integer array,. It just wants a raw address.

- **`value`:** The exact value you want to write into the memory. 

- **`num`:** A `size_t` telling the function exactly how many bytes of memory to overwrite.

It return the exact pointer you gave it, just a feature which was useful in old days and so never removed, we obviously don't need the pointer back and the return value is almost never used nowadays
