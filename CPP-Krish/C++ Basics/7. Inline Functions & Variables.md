As seen in assembly code, there is slight overhead to function calls, which may be negligible in comparison to actual runtime of the function logic for large functions but noticeable for smaller functions.

**Inline expansion** is a process where a function call is replaced by the code from the called function’s definition. But the cost is that the executable will grow larger. Larger executables tend to be slower (due to not fitting as well in memory caches).

 Inline expansion could result in performance improvements, performance reductions, or no change to performance at all, depending on the relative cost of a function call, the size of the function, and what other optimisations can be performed (the function calls may be inlined and become constant expressions computable at compile time).

Not all functions can be inlined. Example: A function whose definition is in another translation unit. Since the compiler can’t see the definition for such a function, it doesn’t know what to replace the function call with.

 A modern compiler will assess each function and each function call to make a determination about whether that particular function call would benefit from inline expansion. A compiler might decide to expand none, some, or all of the function calls to a given function.

Historically, compilers either didn’t have the capability to determine whether inline expansion would be beneficial, or were not very good at it. For this reason, C++ provided the keyword `inline`, which was originally intended to be used as a hint to the compiler that a function would (probably) benefit from being expanded inline.

Here’s an example of using the `inline` keyword:

```cpp
inline int min(int x, int y)  {
    return (x < y) ? x : y;
    // inline keyword means this function is an inline function
}
int main() {
    cout << min(5, 6) << '\n';
    cout << min(3, 2) << '\n';
    // Note that after inlining they can be computed at compile time.
}
```

However, in modern C++, the `inline` keyword is no longer used to request that a function be expanded inline because

- Misuse could actually harm performance.
- The `inline` keyword is just a hint. The compiler is completely free to ignore the request. The compiler is also free to perform inline expansion of functions that do not use the `inline` keyword.
- We use the `inline` keyword on a function definition, but inline expansion is actually determined per function call. It may be beneficial to expand some function calls and detrimental to expand others, and there is no syntax to influence this.
- Modern optimising compilers are better than humans in most cases for deciding.

In modern C++, the term `inline` has evolved to mean “multiple definitions are allowed”. Thus, an inline function is one that is allowed to be defined in multiple translation units (without violating the ODR).

Inline functions have two primary requirements:
- The compiler needs to be able to see the full definition of an inline function in each translation unit where the function is used (a forward declaration will not suffice on its own) or else the linker may not find the definition and give error. Only one such definition can occur per translation unit, otherwise a compilation error will occur.
- The definition can occur after the point of use if a forward declaration is also provided. However, the compiler will likely not be able to perform inline expansion until it has seen the definition (so any uses between the declaration and definition will probably not be candidates for inline expansion).
- Every definition for an inline function (with external linkage, which functions have by default) must be identical, otherwise undefined behaviour will result. 

The linker will consolidate all inline function definitions for an identifier into a single definition (thus still meeting the requirements of the one definition rule). If there are different definitions in different files then obviously compiler will not recognise it (as it only sees one translation unit), and linker won't bother to check (optimisation), it will just pick the first definition it finds and link all the calls to this definition, so you can see why this would cause undefined behaviour.

This actually makes our program IFNDR (Ill formed, no diagnostic required). This essentially means your code is invalid and invokes Undefined Behavior, but the compiler is not obligated to throw an error or warn you about it.

- **Ill-Formed:** This means your code violates the fundamental rules of the C++ language. It is illegal C++ code.
- **No Diagnostic Required:** This is the standard explicitly giving the compiler permission to look the other way. It means the compiler does _not_ have to issue an error, it does _not_ have to stop the build, and it doesn't even have to give you a warning.


The following works because of `inline`. If removed, it will be an ODR violation.

main.cpp:
```cpp
double circumference(double radius); // forward declaration
inline double pi() { return 3.14159; }

int main() {
    cout << pi() << '\n';
    cout << circumference(2.0) << '\n';
}
```

math.cpp
```cpp
inline double pi() { return 3.14159; }
double circumference(double radius) {
    return 2.0 * pi() * radius;
}
```

The old use and the new use may feel completely unrelated but are not becuase you see, for having inlining capability, the compiler needs to see the definition within the same translation unit, so the modern use case actually helps us achieve that by overriding the ODR rule.

Inline functions are typically defined in header files, where they can be `#included` into the top of any code file that needs to see the full definition of the identifier. This ensures that all inline definitions for an identifier are identical.

This is particularly useful for **header-only libraries**, which are one or more header files that implement some capability (no .cpp files are included). Header-only libraries are popular because there are no source files that need to be added to a project to use them and nothing that needs to be linked. You simply `#include` the header-only library and then can use it.

Best practice: Avoid the use of the `inline` keyword unless you have a specific, compelling reason to do so (e.g. you’re defining those functions or variables in a header file).

Why not make all functions inline and defined in a header file?
Mainly because doing so can increase your compile times significantly as the copies exist during compiling as the linker deduplicates them after compilation. Conversely, a function defined in a source file will have its definition compiled only once, no matter how many translation units its forward declaration is included into.
Secondly, if a function defined in a source file changes, only that single source file needs to be recompiled. When an inline function in a header file changes, every code file that includes that header (either directly or via another header) needs to recompiled.

### Inline variables: C++17

C++17 introduces **inline variables**, which are variables that are allowed to be defined in multiple files. Inline variables work similarly to inline functions, and have the same requirements (the compiler must be able to see an identical full definition everywhere the variable is used).

Constexpr functions are inline by default, whereas constexpr variables are not. 
There is one exception: Static constexpr data members are implicitly inline [15.6 -- Static member variables](https://www.learncpp.com/cpp-tutorial/static-member-variables/).

Before C++17, the most convenient way to use global constants across the codebase was to have `constants.h`,

```cpp
#ifndef CONSTANTS_H
#define CONSTANTS_H

namespace constants {
    // Global constants have internal linkage by default
    constexpr double pi { 3.14159 };
    constexpr double avogadro { 6.0221413e23 };
    constexpr double myGravity { 9.2 }; 
    // ... other related constants
}
#endif
```

When this header gets `#included` into a .cpp file, each of these variables defined in the header will be copied into that code file at the point of inclusion.
Because const globals have internal linkage, each .cpp file gets an independent version of the global variable that the linker can’t see. In most cases, because these are constexpr, the compiler will simply optimise the variables away (i.e., replace the look up of variables with actual constant value in the assembly).

Now there are problems if they are `#included` in too many files:
1. Changing a single constant value would require recompiling every file that includes the constants header
2. If the constants are large in size and can’t be optimised away, this can use a lot of memory.

---
### Global constants as external variables

 In this method, we’ll define the constants in a .cpp file (to ensure the definitions only exist in one place), and put forward declarations in the header (which will be included by other files).

constants.cpp:
```cpp
#include "constants.h"
namespace constants {
    // We use extern to ensure these have external linkage
    extern constexpr double pi { 3.14159 };
    extern constexpr double avogadro { 6.0221413e23 };
    extern constexpr double myGravity { 9.2 };
}
```

constants.h:
```cpp
#ifndef CONSTANTS_H
#define CONSTANTS_H

namespace constants {
    // Since the actual variables are inside a namespace, the forward declarations need to be inside a namespace as well
    // We can't forward declare variables as constexpr, but we can forward declare them as (runtime) const
    extern const double pi;
    extern const double avogadro;
    extern const double myGravity;
}

#endif
```

Now we can do `#include "constants.h"` wherever we need them.
The symbolic constants will get instantiated only once (in constants.cpp) instead of multiple code file, and all uses of these constants will be linked to the version instantiated in constants.cpp. Any changes made to constants.cpp will require recompiling only constants.cpp.

But there is a downside as only the variable definitions are constexpr (the forward declarations can't be), these constants are constant expressions only within the file they are actually defined in (_constants.cpp_). In other files, the compiler will only see the forward declaration which is resolved by the linker. This means outside of the file where they are defined, these variables can’t be used in a constant expression. 

Given the above downsides, prefer defining your constants in a header file (either per the prior section, or per the next section). If you find that the values for your constants are changing a lot (e.g. because you are tuning the program) and this is leading to long compilation times, you can temporarily move just the offending constants into a .cpp file (using this method) as needed.

Advantages:
- Works prior to C++17.
- Only one copy of each variable is required.
- Only requires recompilation of one file if the value of a constant changes.

Disadvantages:
- Forward declarations and variable definitions are in separate files, and must be kept in sync.
- Variables not usable in constant expressions outside of the file in which they are defined.

### Global constants as inline variables: C++17

By making our constexpr variables inline, we can define them in a header file and then `#include `them into any .cpp file that requires them. This avoids both ODR violations and the downside of duplicated variables and maintain the constexpr properties. 

This is good as linker will dedupe all the constexpr from all the generated assemblies of different files that `#incldues` it.

Reminder: 
1. Inline variables have external linkage by default, so that they are visible to the linker.
2. Constexpr functions are implicitly inline, but constexpr variables are not implicitly inline. If you want an inline constexpr variable, you must explicitly mark it as `inline`.

constants.h:
```cpp
#ifndef CONSTANTS_H
#define CONSTANTS_H

// define your own namespace to hold constants
namespace constants {
    inline constexpr double pi { 3.14159 }; // note: now inline constexpr
    inline constexpr double avogadro { 6.0221413e23 };
    inline constexpr double myGravity { 9.2 }; 
    // ... other related constants
}
#endif
```

We can include `constants.h` into as many code files as we want, but these variables will only be instantiated once and shared across all code files. Although this method does retain the downside of requiring every file that includes the constants header be recompiled if any constant value is changed.

Advantages:
- Can be used in constant expressions in any translation unit that includes them.
- Only one copy of each variable is required.

Downsides:
- Only works in C++17 onward.
- Changing anything in the header file requires recompiling files including the header.
