### What is Boost.Asio an abstraction over?

It is an abstraction layer over **OS-level I/O Demultiplexers**

Every operating system has a different,  C-API for handling thousands of sockets:

- **Linux:** Uses `epoll` (or `io_uring`).
- **macOS / FreeBSD:** Uses `kqueue`.
- **Windows:** Uses `IOCP` (I/O Completion Ports).

If you wrote a `epoll` server in C++, it would fail to compile on a Windows machine. 
Boost.Asio solves this hardware fragmentation. You write one set of generic C++ networking code, and Asio's internal preprocessor macros silently translates your C++ into pure `epoll`, `kqueue`, or `IOCP` C-structs based on your OS.

---
### The Architectural Shift: Reactor vs. Proactor

### 1. The Reactor Pattern

- Your C++ application registers a File Descriptor (FD) with an OS-level event multiplexer (like `epoll`). Your thread goes to sleep.

- When the NIC hardware drops a packet into RAM, the OS Kernel processes the TCP headers and places the payload into the socket's internal **Kernel-Space Receive Buffer**. The OS then wakes up your C++ thread to announce: _"FD 5 is now readable."_

- Your application thread is awake, but the data is still trapped inside the Kernel. Your thread must manually execute a synchronous `recv()` system call. This forces a CPU context switch, crossing the security boundary to physically copy the bytes from the Kernel's buffer into your C++ User-Space array.

### 2. The Proactor Pattern

- **The Registration:** Your C++ application initiates an asynchronous I/O operation (e.g., `async_read`). You hand the I/O engine two things: a pointer to a pre-allocated **User-Space buffer**, and a completion handler (a lambda callback). Your thread yields the CPU.

- **The Background Transfer:** When the packet arrives, the underlying system handles the memory transfer entirely in the background. Asio automatically performs the `recv()` system call and copies the bytes from Kernel Space directly into your pre-allocated User-Space buffer.

- **The Execution Benefit:** The C++ business logic thread does absolutely zero data copying. It is only scheduled to wake up and execute your callback _after_ the memory transfer is 100% complete and the data is already sitting securely in your User-Space variables.

---

**Note:** If you compile Boost.Asio on a modern Linux kernel, Asio can  completely bypass `epoll` and map its Proactor directly to `io_uring` (which is a native OS-level Proactor). It removes the faking it step entirely!. Since `io_uring` is relatively new, many older hardwares do not have it and so Boost.Asio defaults to `epoll`.

### Optimisations by Boost

Without `io_uring`, Boost.Asio running on Linux is fundamentally just a wrapper around `epoll`. It does not eliminate any CPU context switch, so no optimisations at the Kernel Level.

However, if we look at **User Space** (your C++ code), Asio provides massive optimisations that are incredibly difficult to write yourself. 

#### 1. The Thread Pool 

In our raw `epoll` notes, scaling to 8 CPU cores required us to manually write Thread-Safe Queues, Condition Variables, Mutexes, and `EPOLLONESHOT` flags.

In Asio, you create a thread pool by simply calling `io_context.run()` from multiple threads:

```cpp
boost::asio::io_context io_context;
// ... setup sockets ...

// Spawn 8 threads that all dive into the exact same io_context
std::vector<std::thread> pool;
for(int i = 0; i < 8; ++i) {
    pool.emplace_back([&io_context](){ io_context.run(); });
}
```

Asio's internal engine acts as a lock-free load balancer, distributing the incoming data and lambda callbacks across all 8 threads perfectly, without you ever having to write a `std::mutex`.

#### 2. Strand

When you have 8 threads running `io_context.run()`, what happens if Thread 1 and Thread 2 both try to execute a callback for the _same_ client at the exact same time? You get a race condition.

**The Scenario:** Race condition occurs when a **Network Read** collides with an **Asynchronous Timer** (like a 30-second Keep-Alive timeout). If the timer fires at the exact same microsecond a delayed network packet arrives, Thread 1 executes the timeout (deleting the socket) while Thread 2 executes the read (writing to the deleted socket).

Normally, you would fix this by putting a `std::mutex` inside your lambda function. But Mutexes are slow.

Asio invented the **Strand**. If you wrap your callbacks in a Strand, Asio guarantees that those specific callbacks will run strictly sequentially, even if 8 different threads are executing them. It provides 100% thread safety without ever using a blocking OS-level Mutex.

A Strand is a tiny, private sub-queue with an "In Progress" sign on it.

If you wrap  two lambdas in a Strand, here is how Asio avoids putting anyone to sleep:

1. Thread 1 grabs **Task 1**. It flips the Strand's sign to _"In Progress"_ and starts doing the math.
2. Thread 2 grabs **Task 2**.
3. Thread 2 looks at the Strand and sees the _"In Progress"_ sign.
4. Thread 2 does **NOT** wait. It drops Task 2 into the Strand's private queue and leaves
5. Thread 2 instantly goes back to the main Task Queue, grabs a task for another client, and keeps the CPU running at 100% speed.
6. When Thread 1 finishes Task 1, it checks the Strand's private queue, sees Task 2 sitting there, and executes it itself!

#### 3. Memory Allocation

Every time you create a lambda function (your callback handler), C++ has to allocate memory on the Heap for it. Asio silently intercepts these allocations. Instead of asking the OS for new memory every time, Asio maintains its own pre-allocated **Memory Pools**. It recycles the memory blocks for your lambda functions, bypassing the OS memory manager entirely and keeping your CPU running at maximum speed.
To understand exactly what Asio is doing here, we have to look at why lambdas need memory in the first place, and why asking the Operating System for it is so slow.

###  A. Why does a Lambda need memory?

When you write a normal C++ function, its variables live on the **Stack**, which is incredibly fast and cleans itself up instantly.

But asynchronous callbacks (lambdas) are different. When you call `async_read(..., [this, self](){ ... })`, your lambda captures variables like `this` and `self` so it can use them later. Because the original function finishes and destroys its Stack immediately, the lambda's "backpack" of captured variables must be moved to the **Heap** to survive until the OS Kernel finishes the network read.
By default, C++ puts it on the Heap by calling `new`.

### B. The Problem: The OS Memory Manager is Slow

Every time C++ calls `new` or `malloc`, it has to talk to the Operating System's Memory Manager.

- The OS has to search your system's RAM for an empty block of the exact right size.
    
- The OS has to deal with "Fragmentation" (scattered chunks of used memory).
    
- **The Killer:** The OS Memory Manager is a shared resource. If your 8-core server has 8 threads all trying to create lambdas at the exact same time, the OS puts a global Mutex lock on the RAM. 7 threads go to sleep while 1 thread gets its memory.

If you have 10,000 clients sending messages every second, your server is executing 10,000 `new` and `delete` operations per second. Your CPU spends more time begging the OS for memory than actually processing game logic.

###  C. The Solution: Asio's Custom Memory Pool

Boost.Asio looks at this process and says, _"We are generating thousands of lambdas that are all roughly the exact same size, and they only live for a few milliseconds. Asking the OS for custom space every single time is a waste."_

So, Asio intercepts the process and uses a **Memory Pool**.

Here is how Asio bypasses the OS entirely:

1. **The Big Grab:** When your server starts, Asio goes to the OS exactly _once_ and asks for one massive, continuous chunk of RAM.
    
2. **The Slicer:** Asio slices that massive chunk into thousands of perfectly sized, reusable slots (the Memory Pool).
    
3. **The Interception:** When your C++ code creates a new lambda, Asio intercepts the `new` command. It does not talk to the OS. Instead, it just grabs an empty slot from its own private pool and shoves the lambda in there. This takes practically zero CPU cycles.
    
4. **The Recycling:** When the lambda finishes executing, Asio does not call `delete` to give the memory back to the OS. It simply flips a flag on that slot saying, _"This space is empty and ready to be overwritten by the next lambda."_

---
#### The Two Lists of Asio

Asio physically maintains **two completely separate lists** in memory.

Inside the `io_context`, Asio manages two distinct areas:

1. **The Pending I/O Dictionary:** When you call `async_read`, Asio puts your lambda function here and links it to your socket's File Descriptor. It means: _"We are waiting on the OS Kernel for this."_

Asio reaches down into the OS and uses `epoll_ctl()` to add FD `5` to the Kernel's **Red-Black tree**.  Asio takes your `my_lambda` and saves it in its own **Pending I/O Dictionary** in User Space, mapped to the number `5`. (You can have at-most one lambda for read at FD 5, and at-most one for write at FD 5, having multiple is disastrous for obvious reasons.)

2. **The Ready Task Queue:** This is the execution line. It is a standard thread-safe queue. If a lambda is in here, it means the Kernel is completely finished, the data is sitting in your buffer, and the lambda is ready to be executed by the CPU.

#### The Complete Event Loop Flow

##### 1. Initial Step

Before you even start the loop, your main thread executes a command like `async_read(socket, buffer, my_lambda)`.

- Asio registers the `socket` with the OS Kernel's `epoll` instance.
- Asio takes `my_lambda` and places it in the **Pending I/O Dictionary**.
- _State check: The Ready Task Queue is currently empty._

##### 2. The Threads Dive

You spawn 4 C++ threads and tell them all to execute `io_context.run()`.

- The 4 threads enter Asio's internal `while(true)` loop.
- They look at the **Ready Task Queue**. It is empty.
- Because there is no C++ code ready to execute, Asio commands all 4 threads to dive down into the OS Kernel and call `epoll_wait()`.
- _State check: All 4 threads are put to sleep by the OS. 0% CPU utilization._

##### 3. The Kernel Wakeup

100 different clients just sent data.

- The OS Kernel drops the packets into the 100 different socket Receive Buffers.
- The OS Kernel looks at `epoll`, sees the data, and wakes up **Thread 1**.
- Threads 2, 3, and 4 are deliberately left asleep by the OS to prevent the Thundering Herd problem (they would go to call recv() but find that it is empty, so wasted context switches).

##### 4. The Emulated Proactor

Thread 1 is awake, but it is _not_ running your C++ code yet. It is running Asio's internal engine logic.

- Thread 1 loops over the 100 sockets that have data.
- For every single socket, Thread 1 calls the POSIX `recv()` function, copying the data out of the Kernel and into your C++ buffers.
- **The Handoff:** As Thread 1 finishes copying the data for a socket, it goes to the **Pending I/O Dictionary**, finds the matching lambda function, pulls it out, and drops it into the **Ready Task Queue**.

##### 5. The Execution Swarm

Now, the **Ready Task Queue** contains 100 lambdas that are fully populated with data and ready to run.

- Asio rings an internal bell to wake up Threads 2, 3, and 4.
- Now, all 4 threads swarm the **Ready Task Queue**.
- Thread 1 grabs a lambda and executes your business logic.
- Thread 2 grabs a lambda and executes your business logic.
- They continuously pop lambdas off the queue until it is completely empty.

##### 6. The Loop Resets

Once all 100 lambdas have been executed, the **Ready Task Queue** is empty again.

- The 4 threads loop back around.
- They see the queue is empty, so they dive right back down into the OS Kernel, call `epoll_wait()`, and go back to sleep.

### Example Code

```cpp
#include <iostream>
#include <memory>
#include <utility>
#include <boost/asio.hpp>

using boost::asio::ip::tcp;

class Session : public std::enable_shared_from_this<Session> {
private:
    tcp::socket socket_;
    char data_[1024]; 

public:
    Session(tcp::socket socket) : socket_(std::move(socket)) {}

    void start() { 
        do_read(); 
    }

private:
    void do_read() {
        // We create a smart pointer,'self', that points to this specific client.
        // As long as 'self' exists, this Session cannot be deleted from RAM.
        auto self(shared_from_this()); 
		
		// this is the raw pointer
		// self is a shared pointer
        socket_.async_read_some(boost::asio::buffer(data_, 1024),
            [this, self](boost::system::error_code ec, std::size_t length) {
                // When the blind thread pulls this lambda from the Task Queue, 
                // it unpacks the backpack. It uses 'this' to know exactly which 
                // client's data_ array it just filled!
                if (!ec) {
                    do_write(length); 
                }
            });
    }

    void do_write(std::size_t length) {
        auto self(shared_from_this());
        
        boost::asio::async_write(socket_, boost::asio::buffer(data_, length),
            [this, self](boost::system::error_code ec, std::size_t length) {
                if (!ec) {
                    do_read(); // Loop back and wait for the next message
                }
            });
    }
};

class Server {
private:
    tcp::acceptor acceptor_; // Receptionist

public:
    Server(boost::asio::io_context& io_context, short port)
        : acceptor_(io_context, tcp::endpoint(tcp::v4(), port)) {
        do_accept();
    }

private:
    void do_accept() {
        acceptor_.async_accept(
            [this](boost::system::error_code ec, tcp::socket socket) {
                if (!ec) {
                    // Create a new Session in RAM and start it
                    std::make_shared<Session>(std::move(socket))->start();
                }
                do_accept(); 
            });
    }
};

int main() {
    boost::asio::io_context io_context;
    Server s(io_context, 8080);
    
    // The thread dives into the OS Kernel here and goes to sleep
    io_context.run(); 
    return 0;
}
```

#### 1. async_read vs async_read_some
- async_read is directly called, and socket is passed to the function while async_read_some is called as the socket's function(async_read(socket, buffer, lambda), socket.async_read_some(buffer, lambda))
- async_read doesn't return before the whole buffer is full while async_read_some may return without filling the buffer
#### 1. The Lambda Backpack

- The Task Queue doesn't know about FDs or clients; it just holds C++ functions.
- When you create the lambda, the compiler builds an invisible `struct` (a backpack) that carries a pointer to the specific Client object (because of `[this, self]`) capture. When the thread executes the lambda, the lambda unpacks the pointer and knows exactly whose data it is modifying.

#### 2. The Memory Lifetime Problem (`std::shared_ptr`)

Because asynchronous operations might finish 5 seconds after you requested them, you need a guarantee that the Client object hasn't been deleted from RAM while the OS Kernel was working.

In Asio, you never use raw pointers. You structure your clients as `Session` classes that inherit from `std::enable_shared_from_this`. You capture a `shared_ptr` (`self`) inside every single lambda's backpack. This mechanically forces the C++ memory manager to keep the `Session` alive in RAM as long as Asio still has a lambda sitting in the queue.

#### 3. Why inherit? Why not just make a `shared_ptr` yourself?

You might try to create the smart pointer inside `do_read()` like this:
```cpp
void do_read() {
    std::shared_ptr<Session> self(this); 
    // ...
}
```

When you create a `std::shared_ptr`, C++ allocates a **Control Block** in RAM. The Control Block holds the Reference Count (e.g., `Count = 1`).

1. When the client first connected, the Acceptor created the original smart pointer: `std::make_shared<Session>()`. C++ created **Control Block A**.
2. If you later run `std::shared_ptr<Session>(this)` inside the class, C++ doesn't know about Control Block A. It  creates a brand new **Control Block B** for the exact same memory address.
3. You now have two completely independent Reference Counters managing the exact same physical piece of RAM.
4. When Control Block A hits `0`, it deletes the memory.
5. A millisecond later, Control Block B hits `0`, and tries to delete the _exact same memory again_.

This is called a **Double Free**, and it is an unrecoverable system crash.

**The Solution:** By inheriting from `std::enable_shared_from_this`, your `Session` class is secretly given a hidden `weak_ptr` connecting it to the original Control Block A. When you call `shared_from_this()`, , C++ takes that hidden `weak_ptr` and temporarily upgrades it to a `shared_ptr` _just_ for the lambda's backpack. When the lambda finishes, that temporary `shared_ptr` is destroyed, the count drops back down safely, and the object can be deleted.

#### 4. Aren't this `this` and `self` pointing to the same thing ? 

Yes. but we backpack both because `this` allows for easier syntax as the compile will automatically insert `this->` to any class variable, whereas if it were not present then we would have to explicitly deference using `self->`.

### 5. Who is providing the arguements to the lambdas when they run ?

The lambdas are stored as structs, and the arguments become member variables.
The kernel sets their value.

### Callback Hell

Consider this sequence of events that needs to be programmed:

1. **Read** the player's username.
2. **Query** the asynchronous database to see if the user exists.
3. **Read** the player's password.
4. **Write** a "Login Successful" message back to the player.


Because every single one of those 4 steps requires a round-trip to the OS Kernel or the Database, we have to use `async_`.

```cpp
void login_sequence() {
    auto self(shared_from_this());

    // STEP 1: Read Username
    boost::asio::async_read(socket_, buffer_user, 
        [this, self](boost::system::error_code ec, std::size_t) {
            if (!ec) {
                
                // STEP 2: Query the Database
                db_.async_query(buffer_user.data(), 
                    [this, self](boost::system::error_code ec, DatabaseResult db_res) {
                        if (!ec && db_res.user_exists) {
                            
                            // STEP 3: Read Password
                            boost::asio::async_read(socket_, buffer_pass, 
                                [this, self, db_res](boost::system::error_code ec, std::size_t) {
                                    if (!ec && verify_pass(db_res, buffer_pass)) {
                                        
                                        // STEP 4: Write Success
                                        boost::asio::async_write(socket_, buffer_success, 
                                            [this, self](boost::system::error_code ec, std::size_t) {
                                                if (!ec) {
                                                    start_game();
                                                } else { handle_error("Write failed"); }
                                            });
                                    } else { handle_error("Bad Password"); }
                                });
                        } else { handle_error("User not found"); }
                    });
            } else { handle_error("Read failed"); }
        });
}
```

**Scoping Nightmare:** Notice how Step 3 needs the `db_res` variable from Step 2? To get it there, we had to manually pack `db_res` into Step 3's lambda backpack `[this, self, db_res]`. If you have 10 steps, the backpacks become massive, copying variables over and over.

### Coroutines: C++-20

#### 1. The Limitations of Standard Functions

In standard C++, when you call a function, the compiler puts all of its local variables onto the **Call Stack**. The Call Stack has a strict  rule: **When a function returns, its Stack memory is instantly destroyed.**

Because of this, if a function needs to wait 5 seconds for network data, it has two choices:

1. **Block the thread:** Go to sleep and hold the thread hostage so the Stack isn't destroyed 
2. **Use a Lambda:** Pack all the variables into a backpack on the Heap, return immediately so the thread can do other work, and let the lambda execute later (Callback Hell).

#### 2. The Coroutine Frame (The Heap)

When you put the word `co_await` inside a function, instead of putting your local variables on the Call Stack, compiler allocates a durable box in RAM called the **Coroutine Frame** (on the Heap).

This frame holds:

1. All your local variables.
2. The function's parameters.
3. An **Instruction Pointer** (a bookmark remembering exactly what line of code you are currently on).    

#### 3. The Execution Flow (Pause and Resume)

```cpp
// 1. The thread starts executing. Variables are safe in the Coroutine Frame.
boost::asio::awaitable<void> login_sequence() {
    
    // 2. The thread hits co_await. 
    co_await boost::asio::async_read(socket, buffer, boost::asio::use_awaitable);

    // 4. The thread resumes exactly here!
    process_data(buffer);
}
```

#### Step 1: The Pause and Package

When Thread 1 hits `co_await async_read(...)`:

1. The C++ compiler  pauses the function and generates the `std::coroutine_handle` (a specialised pointer).

2. Asio takes that pointer and files it into the **Pending I/O Dictionary**, mapping it to the socket's File Descriptor (e.g., `[FD 5 + READ] -> coroutine_handle`).

3. Thread 1 executes its invisible `return`, leaves the function entirely, and goes back to the `io_context` loop.

#### Step 2: The Transfer

Five seconds later, the OS Kernel receives the network packet. It rings the `epoll` alarm and wakes up a thread (let's say Thread 1 again). Thread 1 executes Asio's internal engine logic:

1. It copies the network bytes out of the Kernel into your buffer.
2. It looks up `[FD 5 + READ]` in the **Pending I/O Dictionary**.
3. It finds the  `std::coroutine_handle`.
4. Thread 1 moves it out of the Dictionary and drops it into the **Ready Task Queue**.

#### Step 3: Resume

Meanwhile, **Thread 2** is looking for work.

1. Thread 2 pulls the handle out of the **Ready Task Queue**.
2. Thread 2 has no idea what this coroutine is or what it does.  It executes a built-in C++ command called `handle.resume()`.
3. The moment Thread 2 calls `.resume()`, the CPU looks at the memory address stored in the handle and teleports Thread 2's execution state directly inside your Coroutine Frame.

Thread 2 picks up on the exact line of code immediately following the `co_await`, with all your local variables exactly as you left them.
