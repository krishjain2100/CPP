**POSIX Socket API** is a standardised set of C functions that allows the program to talk to the kernel's network stack. 

---
Side note: An IP address is associated with every NIC so the system could have multiple IP addresses if using more than one NIC. Also new RX/TX rings are allocated per NIC.

### 1. `socket()` 

Before you can receive data, you must ask the OS Kernel to allocate memory for a new networking File Descriptor and a set of internal, private software buffers (queues) (the Send Buffer (SO_SNDBF) and Receive Buffer (SO_RCVBF))

```cpp
int server_fd = socket(int domain, int type, int protocol);
```

- **`domain`:** Tells the kernel which addressing family to use.
    - `AF_INET`: Use IPv4 (32-bit addresses)
    - `AF_INET6`: Use IPv6 (128-bit addresses)

- **`type`:** Tells the kernel what kind of state machine to attach to this socket.
    - `SOCK_STREAM`: Use TCP
    - `SOCK_DGRAM`: Use UDP

- **`protocol`:** Usually set to `0` to let the OS automatically choose the default protocol for the given `type` (e.g., it will choose TCP for `SOCK_STREAM`).

- **Returns:** An integer (the File Descriptor, e.g., `3`). If it fails, it returns `-1`.

By separating `type` and `protocol`, the OS gives you a choice:

- `socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)`: _"Kernel, I want to use TCP, and I want YOU to handle all the math. Just give me a clean stream of data."_
- `socket(AF_INET, SOCK_RAW, IPPROTO_TCP)`: _"Kernel, I want to use TCP, but step aside. I am building the raw 1s and 0s of the headers manually in my C++ code."

You might wonder if `SOCK_RAW` means "step aside, I'm doing the TCP math," why do you still have to pass `IPPROTO_TCP` to the OS?

1. Outbound: The IP Header "Protocol" Field:
	When your C++ code generates a raw TCP header and a payload, you hand that chunk of bytes to the OS to send over the internet. Because you used `socket(AF_INET, ...)`, the OS is still responsible for wrapping your raw chunk inside an **IPv4 Header** before firing it out of the network card. Every IPv4 header has a mandatory 8-bit field called the `Protocol` field. This field tells the receiving computer what kind of data is hidden inside the IP packet.

2. Inbound: The Kernel's Bouncer (Filtering)
	A server might receive 100,000 packets a second from the internet. When a packet arrives, the OS strips off the Ethernet and IP headers. If you have a raw socket open, the OS needs to know if it should hand a copy of that raw packet to your C++ program.
	
	- If you just said "Give me a raw socket," the OS would have to copy _every single packet_ hitting the machine (TCP, UDP, ICMP ping packets, routing updates) and dump them all into your C++ program. Your program would instantly crash from memory exhaustion.
	- By specifying `IPPROTO_TCP`, you are telling the OS: _"Only wake up my raw socket if the incoming IP header specifically says it contains TCP data. Ignore the UDP and Ping traffic."

Are all TCP packets coming to the server sent to our program in `SOCK_RAW`, even if their port number doesn't match our program: YES
Would the programs for which the packet was actually meant for get the packet: YES, the OS will create a photocopy of it to send to our program

### 2. `bind()`

You have a socket, but the OS doesn't know what traffic to send to it. `bind()` tells the kernel: _"Any packet that arrives at the NIC destined for Port 8080 belongs to File Descriptor 3."_

```cpp
int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```

- **`sockfd`:** The file descriptor you just got from `socket()`.
- **`addr`:** A pointer to a C-struct (`sockaddr_in`) containing two critical pieces of information:
    - **IP Address:** Usually set to `INADDR_ANY` (0.0.0.0), meaning the socket will accept packets from any physical NIC on the motherboard.
    - **Port:** The 16-bit port number (e.g., `8080`). _Note: You must use `htons(8080)` to convert the number into Big-Endian format, which is the mathematical standard the internet uses._
    8080 is 1F 90 in standard hexadecimal, computer stores it as 2 bytes, 90 goes in smaller memory address and 1F in bigger one (Little endian) so that addition could go from LSB to MSB easily, but humans read it left to right so Big Endian is used to transfer data i.e, 1F is sent first then 90.
- **`addrlen`:** The size of the `addr` struct in bytes (usually `sizeof(addr)`).

Might want to hold off any questions till `accept()`.

### 3. `listen()`

This function flips the kernel's TCP state machine from `CLOSED` to `LISTEN`. Now the socket will start accepting connections.

```cpp
int listen(int sockfd, int backlog);
```

- **`sockfd`:** Your server's file descriptor.

- **`backlog`:** This is a crucial security and performance parameter. It tells the OS exactly how many incoming connections it is allowed to hold in the **SYN-Backlog Queue** before it starts rejecting/dropping new `SYN` packets. The (N+1)th simultaneous connection attempt is immediately dropped by the hardware.

---

What we setup above was a listening socket, think of it like the **receptionist** of our program, 
it only handles the handshake with new connections, whatever happens after that happens on the connection socket, that is created using `accept()` which we we will study after this.

The point of connected socket is to handle many different clients, so that the data from each client remain segregated.

Listening socket is identified by a 2-tuple hash(Destination IP+Destination Port)
Connected socket is identified by a 4-tuple hash(Source IP+Source Port+Destination IP+Destination Port)
#### 1. The Listening Socket (2-Tuple)

When you call `bind()` and `listen()` on File Descriptor 3, you create a Listening Socket. Think of this socket as the **Receptionist**. The Receptionist uses a **2-Tuple** (Local IP + Local Port). Its only job is to intercept packets that are trying to start a _brand new_ connection (TCP `SYN` packets).  We will see what happens when both Alice and Bob establish connection to the server at the same time.
#### 2. The Connected Sockets (4-Tuple) 

When Alice's `SYN` packet hits Port 80, the Receptionist (FD 3) handles the 3-way handshake. When the handshake finishes, your C++ code calls `accept()`. ( If `accept()` is not called the accept queue (mentioned in next section) will just keep filling till full, and connections after that will fail)

At this exact moment, the OS Kernel creates a **Brand New Socket** (e.g., FD 4) just for Alice. To ensure Alice's future data goes to FD 4 and _not_ the Receptionist (FD 3), the kernel records Alice's **4-Tuple** in its internal hash table: `[Src IP: Alice's IP, Src Port: 55000, Dst IP: Server IP, Dst Port: 80] -> Maps to FD 4`

When Bob connects a millisecond later, `accept()` creates FD 5. The kernel records Bob's 4-Tuple: `[Src IP: Bob's IP, Src Port: 61234, Dst IP: Server IP, Dst Port: 80] -> Maps to FD 5`

Now, both Alice and Bob start streaming data to Port 80 at the same time. Here is exactly what the OS Kernel does when a packet arrives:
1. **Read the Headers:** The kernel reads the incoming IP and TCP headers to extract the full 4-Tuple.
2. **Check for Established Connections (4-Tuple Match):** It hashes the 4-Tuple and checks its table. If it perfectly matches Alice's 4-Tuple, it drops the payload safely into FD 4's private buffer.
3. **Fallback to the Listener (2-Tuple Match):** What if a new user, Charlie, sends a `SYN` packet? The kernel hashes Charlie's 4-Tuple. It finds _no match_ because Charlie isn't connected yet. As a fallback, it drops the Source IP and Source Port, creates a 2-Tuple (just Dest IP and Dest Port 80), and checks the table again. It finds the Receptionist (FD 3) and hands the `SYN` packet to it to begin the handshake.

### 4. `accept()`

This is where your C++ thread goes to sleep. It tells the OS: "Pause my program. Do not wake me up until a client has successfully completed the 3-way handshake and is sitting in the ESTABLISHED queue."

There are 2 queues allocated for every receptionist socket.

1. **The Accept Queue:** A line for _Clients_ who have finished the 3-way handshake and are waiting for your C++ code to process them.
2. **The Wait Queue:** A line for _Threads_ waiting for work.

When your C++ thread calls `accept()` and the Accept Queue is empty, the OS Kernel physically removes your thread from the CPU's active schedule and drops it into the Receptionist socket's **Wait Queue**. Your thread is now in a `SLEEPING` state (0% CPU).

The microsecond a client finishes a 3-way handshake, the OS drops the client into the Accept Queue, looks at the Wait Queue, sees your C++ thread parked there, and wakes it up to handle the client. 

```cpp
int client_fd = accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
```

- **`sockfd`:** Your listening server file descriptor.

- **`addr`:** A pointer to an empty `sockaddr_in` struct. When the kernel wakes your program up, it fills this struct with the **Client's IP Address** and **Client's Port**, so you know exactly who connected to you.

- **`addrlen`:** A pointer to the size of the `addr` struct.

- **Returns:** A new File Descriptor (e.g., `4`).

The server socket (`3`) NEVER handles data. Its only job is to listen for connections. When a connection is established, OS gives you a new dedicated socket (`4`) just for that client, and the server socket (`3`) goes back to listening.

The `accept()` is run in a while loop so that we can keep handling new connections.

---
### 5. `recv()`

The hardware DMA'd the packet to RAM. The kernel stripped the Ethernet, IP, and TCP headers. The pure payload is sitting in Socket 4's receive buffer. `recv()` moves it into your C++ variables.

Just like the Receptionist socket has a Wait Queue for `accept()`, every connected client socket has its own Wait Queue for `recv()`.  If you call `recv()` and the client's Receive Buffer is currently empty, the OS Kernel physically removes your thread from the CPU and drops it into this specific connected socket's Wait Queue. Your thread consumes 0% CPU until the hardware drops new payload data into the buffer, at which point the Kernel wakes your thread back up to read it.

```cpp
ssize_t recv(int sockfd, void *buf, size_t len, int flags);
```

- **`sockfd`:** The `client_fd` you got from `accept()`.

- **`buf`:** A pointer to a character array in your C++ code (e.g., `char buffer[1024];`).

- **`len`:** The maximum number of bytes you are willing to read (usually the size of your buffer, `1024`).

- **`flags`:** Usually `0`. (Can be used for special kernel instructions, like `MSG_PEEK` to look at the data without removing it from the kernel's buffer).

- **Returns:** The number of bytes actually read. If it returns `0`, it means the client gracefully disconnected (sent a `FIN` packet). If it returns `-1`, an error occurred.

`size_t` is unsigned and `ssize_t` is signed. 
`ssize_t` is used here to allow the return of `-1` for error code as in the POSIX standard, the universal error code is `-1`

`void` is used for `*buf` because the OS does not know what kind of data is being received and doesn't care too. A `void *` is a pointer stripped of all context.

What happens if the client sends two different messages, will I receive them in a single `recv()` call (assuming they both arrive before the thread is woken up): Yes,  the recv just puts all the data in the Rx buffer in your buffer address given, it is upto you to sort out what is a single message. The format or syntax of sending messages is already been agreed during the design phase of server and client, so that does not happen while a connection is being established. Also one message can also be received in two different recv() calls.

What happens if you call the recv() for only 10 bytes but there is 100 bytes sitting in the Rx buffer ? The leftover 90 bytes will sit there patiently waiting for you to call the recv() again.

---
### 6. `send()`

Takes your C++ string and copies it from your application into this specific FD's Send Buffer. The Kernel's network stack reads the data from the private buffer and wraps it in TCP, IP, and Ethernet headers. The Kernel then drops this completed frame into TX Ring. The NIC's MAC chip performs a DMA pull, copying the frame from the TX Ring into the network card, where the PHY chip fires it out the wire.

```cpp
ssize_t send(int sockfd, const void *buf, size_t len, int flags);
```

- **`sockfd`:** The `client_fd`.

- **`buf`:** A pointer to the data you want to send (e.g., `"HTTP/1.1 200 OK"`).

- **`len`:** The exact number of bytes you are sending.

- **`flags`:** Usually `0`.

It returns the number of bytes accepted, if you send 1000 bytes and it returns 400, it means only first 400 bytes were sent. It's your responsibility to send the remaining 600 bytes.
If it returns -1, it means a error has occurred.

---
### 7. `close()`

```cpp
int close(int fd);
```

- **`fd`:** The file descriptor to close.

- **The Action:** Calling this triggers the kernel to send a TCP `FIN` (Finish) packet to the client, perform the 4-way disconnect handshake, and delete this specific FD's private Receive and Send Buffers from system RAM, returning that memory to the OS.

### The Complete C++ TCP Server

```cpp
#include <iostream>
#include <sys/socket.h> // For socket(), bind(), listen(), accept(), send(), recv()
#include <netinet/in.h> // For sockaddr_in and INADDR_ANY
#include <unistd.h>     // For close()
#include <cstring>      // For memset()

int main() {
    // ---------------------------------------------------------
    // 1. socket() - The Receptionist
    // ---------------------------------------------------------
    int server_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (server_fd == -1) {
        std::cerr << "Failed to create socket.\n";
        return 1;
    }

    // ---------------------------------------------------------
    // 2. bind()
    // ---------------------------------------------------------
    struct sockaddr_in server_addr;
    memset(&server_addr, 0, sizeof(server_addr)); // Zero out the struct
    
    server_addr.sin_family = AF_INET;           // IPv4
    server_addr.sin_addr.s_addr = INADDR_ANY; // Listen on all network interfaces (0.0.0.0)
    server_addr.sin_port = htons(8080); // Convert Port 8080 to Big-Endian network bytes

    if (bind(server_fd, (struct sockaddr*)&server_addr, sizeof(server_addr)) == -1) {
        std::cerr << "Failed to bind to port 8080.\n";
        close(server_fd);
        return 1;
    }

    // ---------------------------------------------------------
    // 3. listen()
    // ---------------------------------------------------------
    // Tell the kernel to start accepting SYNs, with a backlog queue of 10.
    if (listen(server_fd, 10) == -1) {
        std::cerr << "Failed to listen.\n";
        close(server_fd);
        return 1;
    }
    
    std::cout << "Server is listening on port 8080...\n";

    // ---------------------------------------------------------
    // The Server Loop
    // ---------------------------------------------------------
    while (true) {
    
        // 4. accept() - The Blocking Handoff
        // The thread goes to sleep at accept() if the Established Queue is 
        // empty. It consumes 0% CPU until then.
        
        struct sockaddr_in client_addr;
        socklen_t client_len = sizeof(client_addr);
        
        int client_fd = accept(server_fd, (struct sockaddr*)&client_addr, &client_len);
        if (client_fd == -1) {
            std::cerr << "Failed to accept client.\n";
            continue;
        }
        
        // The 11th connection won't return -1, it will be as if the SYN packet
        // never came

        std::cout << "Client connected! Kernel gave us FD: " << client_fd << "\n";

        // 5. recv() - Bridging RAM to User Space
        // The thread goes to sleep here again, waiting for the client to send
        // payload data.
        char buffer[1024] = {0}; 
        // This is also blocking, it means that the control goes to OS and wakes this thread up when something is recieved.
        ssize_t bytes_read = recv(client_fd, (void*)buffer, sizeof(buffer), 0);

        if (bytes_read > 0) {
            std::cout << "Received " << bytes_read << " bytes: " << buffer << "\n";
            // 6. send()
            send(client_fd, (const void*)buffer, bytes_read, 0);
        }

        // 7. close()
        // We are done with this client. Send the FIN packet and delete the 
        // private buffers for FD 4.
        close(client_fd);
        std::cout << "Client disconnected. Receptionist is ready for the next client.\n\n";
    }

    // Shut down the main receptionist socket (unreachable in this infinite 
    // loop, but good practice).
    close(server_fd);
    return 0;
}
```

**Why do we have separate sockaddr_in and sockaddr ?**

```cpp
struct sockaddr {
    unsigned short sa_family;    // 2 bytes (The protocol type, e.g., AF_INET)
    char           sa_data[14];  // 14 bytes of raw, unformatted address data
};

struct sockaddr_in {
    short          sin_family; // 2 bytes (Must be set to AF_INET)
    unsigned short sin_port;   // 2 bytes (The Port Number, e.g., 8080)
    struct in_addr sin_addr;   // 4 bytes (The 32-bit IPv4 Address)
    char           sin_zero[8];// 8 bytes of pure PADDING (zeros)
};
```

`sockaddr` is the old type we used, in which we had to manually fill in the 14 bytes of data which was a cumbersome task, but `sockaddr_in` made it easier for us, the `sin_zero` in it is just so it matches the length of `sockaddr`. `sockaddr_in` can be typecasted to `sockaddr` because that is what our functions use.

Why `memset` is used when we are filling the data anyways in `sockaddr_in`? To fill the padding of 8 bytes, it has to be filled with zeros so as to not confuse the os

### Issues with the above code

- **Infinite Blocking:** The server handles exactly one client at a time. If Trader A connects but takes ten seconds to type an order, the server thread falls asleep at `recv()`. Trader B is completely locked out and ignored until Trader A finishes.

- **Hangs Up Immediately:** After receiving exactly one message, it blindly calls `close(client_fd)`. 

- **Buffer Overwrites:** It assumes a single `recv()` call fetches exactly one perfectly formatted message. In reality, TCP is a continuous stream; one `recv()` might pull half a message or three messages fused together.

To fix the **Infinite Blocking** problem, we need a way to tell the OS: _"Don't put my thread to sleep on a single socket. Put my thread to sleep, and wake me up if **ANY** socket has data or a new connection waiting."_ This concept is called **Synchronous I/O Multiplexing**.

---
### 8. `select()`

`select()` was the original POSIX solution to the blocking problem. Instead of blocking on a single `accept()` or `recv()`, `select()` allows a single server process to monitor an array of File Descriptors (FDs) simultaneously.  It relies on fixed-size bit arrays (bitmasks) to track which sockets to watch. So you loop through the watchlist to check which FDs have data.

```cpp
int select(int nfds, fd_set *readfds, fd_set *writefds, fd_set *exceptfds, struct timeval *timeout);
```

- **`nfds`:** The highest file descriptor integer you are monitoring, **plus 1**. (If your highest FD is 5, you pass 6).
- **`readfds`:** A pointer to an `fd_set` bitmask tracking sockets you want to read from.
- **`writefds`:** A pointer to an `fd_set` tracking sockets you want to write to.
- **`timeout`:** A `timeval` struct (seconds and microseconds) determining how long the thread should sleep. Passing `NULL` forces it to block forever until an event occurs.
- **Returns:** The total number of file descriptors that are ready for action, `0` if the timeout triggered, or `-1` if an error occurred.


**Mechanism & Macros**

You must use four standard system macros to modify the watchlist:

- **`FD_ZERO(fd_set *set)`:** Clears the entire bitmask to zeros.
- **`FD_SET(int fd, fd_set *set)`:** Turns on the specific bit representing that File Descriptor.
- **`FD_CLR(int fd, fd_set *set)`:** Removes an FD from the watchlist.
- **`FD_ISSET(int fd, fd_set *set)`:** Checks if the bit for a specific FD is still turned on.

#### The Fatal Flaws of `select()`

While `select()` made concurrent servers possible, it introduced severe performance bottlenecks:

1. **State Destruction:** When an event occurs, `select()` modifies your `fd_set` bitmasks **in-place** to report readiness. Because your original watchlist is destroyed by the kernel's response, you must completely clear (`FD_ZERO`) and rebuild (`FD_SET`) the arrays from scratch on every single iteration of your server's `while` loop.

2. **$O(N)$ Time Complexity:** When `select()` wakes up your thread, it doesn't tell you _which_ socket fired. It forces your program to linearly iterate from `0` all the way up to `nfds - 1`, running `FD_ISSET()` on every single integer to see if it was the one that triggered.

3. **Strict Hard Limits:** The `fd_set` bitmask is strictly bound by a system macro called `FD_SETSIZE` (almost always hardcoded to 1024). `select()`  cannot track file descriptors with an integer value of 1024 or higher, making it completely unviable for large-scale servers.

### 9. `poll()` 

`poll()` achieves the exact same I/O multiplexing, but it replaces the clunky, fixed-size bitmasks with a dynamic array of structs.

```cpp
struct pollfd {
    int fd;        // The File Descriptor you want to watch (e.g., 3, 4, 5)
    short events;  // What you want the Kernel to watch for (e.g., POLLIN)
    short revents; // The Kernel writes here to tell you what happened (e.g., POLLIN)
};
```

_Note: `POLLIN` is a flag meaning "Watch for incoming data."_

```cpp
int poll(struct pollfd *fds, nfds_t nfds, int timeout);
```

- **`fds`:** A pointer to the first element of your `pollfd` array (your watchlist).

- **`nfds`:** The total number of structs in that array.

- **`timeout`:** How long the thread should sleep before giving up (in milliseconds). `-1` blocks forever.

- **Returns:** The number of File Descriptors ready for action.

#### How `poll()` fixes `select()`:

1. **No `FD_SETSIZE` Limit:** Because it uses an array of structs rather than a fixed bitmask, `poll()` has no 1024-socket limit. It can scale up to the maximum open files allowed by the OS.

2. **Clean State Management:** Notice that the struct separates what you ask for (`events`) from what the kernel reports back (`revents`). Because the kernel doesn't destructively overwrite your requests, you can reuse the exact same array loop after loop without rebuilding it from scratch.


**Mechanism:**

1. **Watch the Receptionist:** You add the Receptionist socket (FD 3) to your array with `events = POLLIN`.
2. **Call `poll()`:** Your thread goes to sleep at `poll()`, consuming 0% CPU.
3. Alice sends a `SYN` packet and finishes the 3-way handshake. The Kernel drops Alice into the Accept Queue, finds FD 3 in your watchlist, changes FD 3's `revents` to `POLLIN`, and wakes up your thread.
4. Your C++ code loops through the array, sees that FD 3 has `revents == POLLIN`. Because the Kernel promised a client is already waiting, you can call `accept()` safely. It will execute instantly without putting your thread back to sleep, giving you FD 4 (Alice).
5. You add FD 4 to your `pollfd` array and call `poll()` again. Now the Kernel is watching the Receptionist (FD 3) for new clients AND Alice (FD 4) for incoming trade orders simultaneously.

### `memset()`

**`memset()`** stands for **Memory Set**. It is used to  fill a continuous block of RAM with a specific, repeating byte. It is used as a **Memory Wiper** to clear out "garbage" data before you start using a variable.

In languages like Python or Java, when you create a new variable, the language automatically clears the memory for you behind the scenes. C and C++ prioritise absolute speed, so they **do not** clean up memory

```cpp
struct sockaddr_in server_addr;
```

The OS carves out 16 bytes of RAM for this struct. But those 16 bytes still contain whatever 1s and 0s happened to be left behind by the last program that used that exact physical spot in RAM. If we don't clean it, it will corrupt network data. When we hand it to the Kernel via `bind()`, the Kernel will try to read that garbage and crash. To fix this, we use `memset()` to overwrite every single byte in that struct with exactly `0`.

```cpp
void *memset(void *ptr, int value, size_t num);
```

- **`ptr`:** A `void *` pointing to the starting memory address. It is a `void *` because `memset()` doesn't care if you are wiping a string, an integer array,. It just wants a raw address.

- **`value`:** The exact value you want to write into the memory. 

- **`num`:** A `size_t` telling the function exactly how many bytes of memory to overwrite.

It returns the exact pointer you give it, just a feature which was useful in old days and so never removed, we obviously don't need the pointer back and the return value is almost never used nowadays.

### `poll()` Server Example

```cpp
#include <iostream>
#include <vector>
#include <sys/socket.h>
#include <netinet/in.h>
#include <unistd.h>
#include <cstring>
#include <poll.h>

int main() {
    // 1. Setup the Receptionist
    int server_fd = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in server_addr;
    memset(&server_addr, 0, sizeof(server_addr));
    server_addr.sin_family = AF_INET;
    server_addr.sin_addr.s_addr = INADDR_ANY;
    server_addr.sin_port = htons(8080);

    bind(server_fd, (struct sockaddr*)&server_addr, sizeof(server_addr));
    listen(server_fd, 10);
    std::cout << "poll() server listening on port 8080...\n";

    // 2. Create the dynamic watchlist using a std::vector
    std::vector<struct pollfd> watchlist;
    
    // Add the Receptionist to the watchlist to look for new connections
    watchlist.push_back({server_fd, POLLIN, 0});

    // 3. The Event Loop
    while (true) {
        // Sleep until at least one socket in the vector has action (-1 timeout)
        int ready = poll(watchlist.data(), watchlist.size(), -1);
        if (ready < 0) break;

        // Iterate backwards through the watchlist. 
        // We go backwards so if we erase a disconnected client, it doesn't 
        // shift the indices of the sockets we haven't checked yet!
        for (int i = watchlist.size() - 1; i >= 0; --i) {
            
            // If this specific socket has NO action, skip it
            if ((watchlist[i].revents & POLLIN) == 0) continue;

            // Scenario A: The Receptionist has a new connection!
            if (watchlist[i].fd == server_fd) {
                struct sockaddr_in client_addr;
                socklen_t client_len = sizeof(client_addr);
                
                // Because poll() promised us someone is waiting, this accept() 
                // executes instantly without freezing.
                int client_fd = accept(server_fd, (struct sockaddr*)&client_addr, &client_len);
                
                std::cout << "New Client Connected! FD: " << client_fd << "\n";
                
                // Expand the watchlist to include the new client
                watchlist.push_back({client_fd, POLLIN, 0});
            }
            
            // Scenario B: An existing client sent data!
            else {
                int client_fd = watchlist[i].fd;
                char buffer[1024] = {0};
                
                // Because poll() promised us data is sitting in RAM, 
                // this recv() executes instantly without freezing.
                ssize_t bytes_read = recv(client_fd, buffer, sizeof(buffer), 0);

                if (bytes_read > 0) {
                    std::cout << "[FD " << client_fd << "] sent: " << buffer;
                    send(client_fd, buffer, bytes_read, 0); // Echo back
                } else {
                    // Client disconnected (bytes_read == 0) or network error
                    std::cout << "Client on FD " << client_fd << " disconnected.\n";
                    close(client_fd);
                    watchlist.erase(watchlist.begin() + i); // Safely remove them
                }
            }
        }
    }
    
    close(server_fd);
    return 0;
}
```

While the code above successfully multiplexes connections, it still relies on naive `recv()` and `send()` calls.
- **Partial Reads:** TCP is a stream, not a message protocol. `recv()` might only grab half a message. A robust server must append incoming bytes into a persistent `std::string` buffer for each client and manually parse for a delimiter (like `\n`) before acting.
- **Partial Writes:** Because the sockets are still in default blocking mode, if the OS Send Buffer fills up, `send()` will freeze the thread until it can push the remaining bytes, ruining our concurrent event loop.

### Handling Slow Clients

Up to this point, we have focused on reading data (`POLLIN` / `readfds`). But what happens when you need to send a massive 50MB file, and the client is on a terrible 3G mobile connection? When your C++ program calls `send()`:

1. You loop `send()` rapidly, dumping data into the OS Send Buffer.
2. Because the client is downloading so slowly, the OS Send Buffer fills up to 100% capacity.
3. If you call `send()` again while the buffer is full, your thread will **block** (freeze completely) until the client acknowledges some data and the OS clears up space. This freezes your entire server.

To fix this, we can ask the kernel: **"Is there free space in the OS Send Buffer so I can write data without freezing?"**
- **`select()`:** You pass the socket into the separate `writefds` bitmask.
- **`poll()`:** There is no separate `writefds` array. Instead, you simply add the `POLLOUT` flag to the `events` bitmask of your existing `pollfd` struct (e.g., `fds[i].events = POLLIN | POLLOUT;`).

Your thread goes to sleep. As soon as the slow client receives some data and the OS empties a few kilobytes of the Send Buffer, the kernel wakes your thread up.
- `select()` leaves a `1` in the `writefds` bitmask.
- `poll()` sets the `POLLOUT` flag in the `revents` field.

Both signal: _"Go ahead, there is guaranteed room in the buffer right now."_ 

But you must handle writing very differently than reading. You usually keep the Receptionist and all idle clients marked for reading (`readfds` or `POLLIN`) permanently, because you want to sleep until they say something. However, 99% of the time, the OS Send Buffer is completely empty and ready to accept data. If you permanently mark a client for writing (`writefds` or `POLLOUT`), the multiplexer will look at it, instantly see there is free space, and return immediately without ever putting your thread to sleep. Your `while` loop will spin millions of times a second, spiking your CPU to 100%, just to constantly be told "the send buffer is still empty". So, 

1. **Never** mark a socket for writing by default.
2. When you want to send data, just call `send()`.
3. If `send()` returns a number smaller than what you asked it to send (meaning the buffer hit its limit and only accepted a partial chunk), **then** you mark the socket for writing (`writefds` or `POLLOUT`). The kernel will wake you up the moment more space clears up. You send the remaining chunk.
4. Once your entire message is sent, you **remove** the write flag.

```cpp
#include <iostream>
#include <vector>
#include <unordered_map>
#include <string>
#include <sys/socket.h>
#include <netinet/in.h>
#include <unistd.h>
#include <cstring>
#include <poll.h>

int main() {
    // 1. Setup the Receptionist
    int server_fd = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = INADDR_ANY;
    addr.sin_port = htons(8080);

    bind(server_fd, (struct sockaddr*)&addr, sizeof(addr));
    listen(server_fd, 10);

    std::vector<struct pollfd> watchlist;
    watchlist.push_back({server_fd, POLLIN, 0});

    // 2. The Write Queue: Maps a Client FD to their unsent data
    std::unordered_map<int, std::string> pending_writes;

    while (true) {
        if (poll(watchlist.data(), watchlist.size(), -1) < 0) break;

        for (int i = watchlist.size() - 1; i >= 0; --i) { // iterate backwards so that erasing from between isn't buggy
            int active_fd = watchlist[i].fd;

            // ========================================================
            // SCENARIO A: Waking up to WRITE data (POLLOUT triggered)
            // ========================================================
            if (watchlist[i].revents & POLLOUT) {
                std::string& unsent_data = pending_writes[active_fd];
                
                // We only call send() because poll() promised there is free space
                ssize_t bytes_sent = send(active_fd, unsent_data.c_str(), unsent_data.length(), 0);
                
                if (bytes_sent > 0) {
                    // Erase only the chunk we successfully sent
                    unsent_data.erase(0, bytes_sent);
                }

                // If the buffer is finally empty, STOP asking the kernel to watch for POLLOUT.
                // Otherwise, our while loop will spin millions of times a second.
                if (unsent_data.empty()) {
                    watchlist[i].events &= ~POLLOUT; 
                }
            }

            // ========================================================
            // SCENARIO B: Waking up to READ data (POLLIN triggered)
            // ========================================================
            if (watchlist[i].revents & POLLIN) {
                
                if (active_fd == server_fd) {
                    // Handle New Connection
                    struct sockaddr_in client_addr;
                    socklen_t client_len = sizeof(client_addr);
                    int client_fd = accept(server_fd, (struct sockaddr*)&client_addr, &client_len);
                    
                    if (client_fd >= 0) {
                        watchlist.push_back({client_fd, POLLIN, 0});
                    }
                } 
                else {
                    // Handle Existing Client Data
                    char buffer[1024];
                    ssize_t bytes_read = recv(active_fd, buffer, sizeof(buffer), 0);

                    if (bytes_read > 0) {
                        std::string reply(buffer, bytes_read);
                        
                        // Attempt to send immediately
                        ssize_t bytes_sent = send(active_fd, reply.c_str(), reply.length(), 0);
                        
                        if (bytes_sent < 0) bytes_sent = 0; // Handle errors safely
                        
                        // If send() returned a number smaller than what we asked it to send
                        if ((size_t)bytes_sent < reply.length()) {
                            // 1. Save the unsent leftovers in the map
                            pending_writes[active_fd] += reply.substr(bytes_sent);
                            
                            // 2. Turn ON the POLLOUT alarm for this specific client
                            watchlist[i].events |= POLLOUT;
                        }
                    } 
                    else if (bytes_read == 0) {
                        // Clean up on disconnect
                        close(active_fd);
                        pending_writes.erase(active_fd);
                        watchlist.erase(watchlist.begin() + i);
                    }
                }
            }
        }
    }
    return 0;
}

```


While dynamically toggling `POLLOUT` prevents you from blindly calling `send()` on a full buffer, it still relies on sockets that are fundamentally in blocking mode. If your sockets are left in their default **blocking** mode, the OS kernel retains the right to put your thread to sleep:

1. Suppose Alice sends a packet. The kernel receives it, drops it in the Receive Buffer, and `poll()` wakes up your C++ thread. However, microseconds before your C++ code executes `recv()`, the kernel runs a routine TCP checksum and realizes Alice's packet is corrupted. The kernel silently deletes the packet from the buffer. When your C++ code finally executes `recv()`, the buffer is suddenly empty. Because the socket is blocking, `recv()` refuses to return empty-handed. It physically puts your server thread to sleep, waiting for Alice to send a _new_ packet. Your entire server is now permanently frozen on Alice, ignoring all other clients.

2. Suppose you want to send a 5,000-byte file to a slow client. You wait for `POLLOUT` to trigger. `POLLOUT` simply means _"there is **some** free space in the Send Buffer."_ It does not mean the buffer is completely empty. If `POLLOUT` triggers because exactly 50 bytes of space opened up, and you blindly call `send()` with your 5,000-byte string, the kernel will accept the first 50 bytes. Because the socket is blocking, it will then put your thread to sleep until the slow client acknowledges data and clears out the remaining 4,950 bytes of space. Your server is instantly frozen.

We will see in the next lesson, how non-blocking would help.

### Compile and Run

Open a new terminal and type `nc 127.0.0.1 8080`.
`127.0.0.1`  This is a special IPv4 address. When the OS Kernel sees this IP, it knows not to send the packet down to the physical Network Card. Instead, it performs a U-turn in software (RAM), instantly routing the packet straight back up to your own machine's network stack.

When you hit Enter, Netcat executes a microscopic, highly optimised C program.

1. Netcat instantly calls `socket()` and then calls a POSIX function: `connect()`.
	- This forces your OS Kernel to generate a TCP `SYN` packet and fire it at Port 8080.
	- Your C++ Server's Kernel receives it, finishes the 3-way handshake, and drops Netcat into the Accept Queue.
	- Your frozen C++ thread is violently woken up from `accept()`, prints _"Client connected!"_, and then goes right back to sleep on `recv()`.

2. Netcat then acts as a raw, transparent pipe between your keyboard and the network
	- When you type _"Hello"_ into the Netcat terminal and hit Enter, Netcat reads your keystrokes and immediately calls `send()`.
	- This pushes the text through the kernel, U-turns it tand drops it into your C++ Server's private Receive Buffer. 
	- Your server's `recv()` unblocks, reads the text, and prints it!

3. Because your C++ server then takes that text and uses `send()` to echo it right back, Netcat catches it. Netcat's internal `recv()` triggers, and it prints _"Hello"_ back out to your terminal screen.

We can loosely say that the listener (receptionist) is working asynchronously.  
The C++ program didn't pause its execution during the filling of the queue of incoming clients
